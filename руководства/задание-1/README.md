# Задание 1. Местный каркас агента

> **Основа:** CMU 11-768 AI Agents, Assignment 1 — Build an Agent Harness
>
> **Воспроизводимая официальная версия:** [коммит `67498d8`](https://github.com/cmu-agents/assignment-1/tree/67498d87e36f7b45a2a4ce82d65d1139fb6a51c0)
>
> **Официальное условие на этой версии:** [ASSIGNMENT.md](https://github.com/cmu-agents/assignment-1/blob/67498d87e36f7b45a2a4ce82d65d1139fb6a51c0/ASSIGNMENT.md)
>
> **Рабочая среда руководства:** Windows 11 Pro, llama.cpp, запущенный непосредственно в Windows, и временные Linux-контейнеры Docker Desktop
>
> **Назначение:** самостоятельное изучение устройства агентной системы, а не получение баллов

Языковая модель — программа, которая по входному тексту предлагает вероятное продолжение. Каркас агента — программа-посредник между моделью и средой, в которой разрешено действовать. Модель предлагает следующий шаг, а каркас хранит историю, проверяет вызов инструмента — строго описанного разрешённого действия, — выполняет его и возвращает результат модели. В этом задании такой каркас нужно понять, дописать по частям и проверить на двух применениях: исправлении программы и игре в шахматы.

Руководство рассчитано на читателя, который знает Python и PowerShell, но может впервые встретить Git, Docker, API, автоматические тесты и агентные системы. Git — это система учёта версий: она хранит историю файлов, позволяет увидеть точный состав правки и вернуться к известной исходной точке. Docker создаёт изолированные среды выполнения из подготовленных шаблонов. API задаёт формальный способ обмена запросами и ответами между программами. Автоматический тест запускает код и сопоставляет наблюдаемое поведение с ожидаемым. Части образуют один последовательный путь: сначала проверяется среда, затем строится общий цикл, после этого добавляется память и только потом — второй предметный агент.

Для этого самостоятельного пути не нужны университетская учётная запись, срок сдачи, внешний поставщик вычислений или платный API. Официальное условие остаётся спецификацией учебных TODO, а выполнение и проверка происходят на местном компьютере.

## 1. Кто участвует в работе

Исходная точка — заготовка проекта с незаполненными учебными местами. Цель раздела — не смешать четыре разных роли: из-за такого смешения легко запустить недоверенный код не там или принять сообщение одной системы за доказательство работы другой.

### 1.1. Пользователь

Пользователь руководит опытом:

- даёт программирующему агенту Cursor узкие поручения;
- запускает команды проверки в Windows PowerShell;
- управляет llama.cpp и Docker Desktop;
- просматривает изменения, журналы и результаты;
- решает, достаточно ли доказательств для перехода дальше.

Пользователь не пишет исходники вручную и не принимает фразу «готово» как доказательство.

### 1.2. Программирующий агент Cursor

Это ИИ-агент в Cursor, которому пользователь поручает изменить исходники учебного проекта. Он читает заготовки и тесты, объясняет договор поведения, вносит ограниченную правку и предлагает способ проверки.

Его задача — **строить каркас**, а не изображать работу создаваемого агента. Интерфейс Cursor здесь не объясняется: важны границы поручения и проверка результата.

### 1.3. Местная языковая модель

`Qwen3.6-27B-Q6_K` или сравнительная `gpt-oss-20b-MXFP4` загружается сервером `llama-server.exe` непосредственно в Windows. Каркас обращается к серверу через API — формальный способ обмена запросами и ответами между программами — по адресу:

```text
http://127.0.0.1:8080/v1
```

Модель не меняет проект сама. Она получает сообщения и описания разрешённых инструментов, а в ответ выдаёт текст и структурированные предложения вызвать инструменты.

### 1.4. Создаваемые `CodeAgent` и `ChessAgent`

Это классы и запускаемые программы внутри учебного проекта:

- `CodeAgent` просит местную модель исследовать задачу, выполнять команды в `/testbed` и подготовить патч — текстовое описание изменений файлов;
- `ChessAgent` просит ту же модель выбирать и исследовать шахматные ходы;
- оба должны повторно использовать общий `Agent` и его цикл ReAct.

ReAct — это повторяющийся порядок «получить состояние → выбрать действие → выполнить инструмент → вернуть наблюдение». Инструментом называется строго описанное действие, которое каркас разрешает модели запросить.

```text
программирующий агент Cursor  →  меняет исходники Agent, CodeAgent, ChessAgent
местная языковая модель       →  предлагает действия уже запущенному каркасу
CodeAgent и ChessAgent        →  применяют общий каркас к разным задачам
пользователь                  →  задаёт работу, запускает проверки, оценивает доказательства
```

К разделу 2 можно переходить, если вы можете своими словами объяснить, почему программирующий агент Cursor и `CodeAgent` — не одно и то же и почему ответ модели ещё не является выполненным действием.

## 2. Как проходит один полный цикл

Исходная точка — Cursor может менять учебный код, llama.cpp может отвечать по API, Docker может создавать изолированную Linux-среду. Цель — связать эти части, не смешав доверенный управляющий код и код, предложенный моделью.

```text
1. Пользователь формулирует узкое поручение.
                 |
                 v
2. Программирующий агент Cursor меняет каркас проекта.
                 |
                 v
3. Пользователь запускает проверку или учебный опыт в PowerShell.
                 |
                 v
4. Каркас отправляет историю и описания инструментов
   местной модели через llama.cpp.
                 |
                 v
5. Модель предлагает один или несколько вызовов инструментов.
                 |
                 v
6. Каркас выполняет порождённые команды или Python
   только во временном Linux-контейнере Docker.
                 |
                 v
7. Результат возвращается модели как наблюдение.
   Цикл повторяется до завершения или предела шагов.
                 |
                 v
8. Каркас сохраняет траекторию и другие артефакты,
   а пользователь независимо запускает проверки.
```

Песочница — это ограниченная среда для недоверенных действий. Здесь ею служит контейнер: временный экземпляр заранее собранного образа Linux. Образ — неизменяемый шаблон с файлами и зависимостями; контейнер — отдельный запущенный экземпляр этого шаблона.

Траектория — последовательная запись запросов, ответов, действий и наблюдений. Артефакт — сохранённый результат опыта, например траектория, патч или отчёт.

Правильное и ошибочное поведение различаются так:

```text
Правильно
модель предлагает команду
→ каркас передаёт её Environment.execute
→ команда исполняется в Linux-контейнере
→ вывод возвращается модели

Опасно и запрещено
модель предлагает команду или Python
→ управляющий код запускает их в Windows
→ недоверенный код получает доступ к компьютеру пользователя
```

К следующему разделу можно переходить, если понятно, где работают PowerShell, llama.cpp, управляющий каркас, `/testbed` и порождённый моделью код.

## 3. Что уже готово и что предстоит реализовать

Исходная точка не пуста. Местная инфраструктура уже подготовлена и проверена, поэтому учебная работа сосредоточена на агентном каркасе, а не на замене Modal собственным конструктором контейнеров. Цель раздела — отделить готовые опоры от кода, который ещё предстоит реализовать.

Уже готово:

- `Environment` создаёт временный Linux-контейнер Docker;
- рабочий каталог агента внутри контейнера остаётся `/testbed`;
- публичный договор `Environment.execute` сохранён;
- образ собирается из закреплённой местной копии исходников;
- шахматная служба публикуется через случайный порт только на `127.0.0.1`;
- штатный `with`/`finally` немедленно останавливает и удаляет контейнер;
- `--rm` страхует аварийный обрыв: удаление происходит после `deployment_timeout`, когда процесс контейнера завершится и Docker доступен;
- подготовлены постановки задач, открытые тесты, сценарии оценки и места для артефактов.

`TODO` — метка незавершённого учебного места в коде. TODO в `src/assignment/agent/` намеренно не заполнены. Нужно поэтапно реализовать:

- состояние сообщений, построение запроса и общий цикл ReAct;
- инструменты `CodeAgent`, обработку исправимых ошибок и загрузку навыков;
- сжатие старой истории в рабочую память;
- инструменты `ChessAgent` и безопасный запуск порождённого Python;
- воспроизводимые опыты и проверяемые артефакты.

Навык — хранимая отдельно инструкция для агента, которую каркас сначала показывает кратко, а полностью раскрывает только по запросу модели.

До реализации TODO исходный полный набор тестов закономерно даёт:

```text
11 failed, 4 passed, 4 deselected
```

Это не признак поломки Docker или модели. Падения обозначают ещё не реализованные договоры частей 1–3. Не нужно исправлять тесты или подменять ожидаемое поведение, чтобы скрыть это состояние.

Учебная граница сохраняется во всех частях: руководство не даёт готовых тел TODO, готовых системных запросов, исправления шахматного дефекта, эталонного патча или готовой шахматной стратегии.

### Как устроен каталог `assignment-1`

- `src/assignment/agent/` — исходники общего `Agent`, `CodeAgent`, `ChessAgent` и их инструментов; здесь находится основная учебная работа;
- `tests/` — быстрые открытые тесты договоров каркаса;
- `local_tests/` — проверки настоящей местной инфраструктуры Docker;
- `tasks/` — постановки задач, данные оценки и навыки; их не подгоняют под решение;
- `chess_app/` — закреплённая исходная программа с воспроизводимым дефектом; её не исправляют напрямую;
- `scripts/` — служебные сценарии проверки модели и независимой оценки;
- `artifacts/` — выходной каталог для патчей, траекторий, результатов и отчётов;
- `.env` — местные настройки API; содержимое этого файла не печатают и не помещают в Git;
- `pyproject.toml` и файл блокировки зависимостей — описание среды Python, которую использует `uv`.

Закреплённый коммит Git задаёт одну и ту же исходную версию `chess_app`. Поэтому результат переносится патчем на чистую копию, а не сохраняется как незаметная ручная правка приложения.

К карте частей можно переходить, если вы отличаете готовую инфраструктуру от учебных TODO и понимаете, почему исходные падения тестов ожидаемы.

## 4. Последовательная карта частей 0–3

Исходная точка — четыре связанных руководства. Цель — пройти их в порядке зависимостей: результат предыдущей части становится проверенной опорой следующей.

### [Часть 0. Обзор и подготовка](00-обзор-и-подготовка.md)

**С чего начинаем:** инфраструктура уже установлена, но её состояние нужно подтвердить.

**Что делаем:** различаем Windows и Linux-контейнер, проверяем Docker, закреплённые исходники, `.env`, llama.cpp, API моделей, ограничения и очистку.

**Зачем первой:** ошибка среды внешне похожа на ошибку каркаса. Часть 0 позволяет не отлаживать TODO при неработающем Docker или неверном псевдониме модели.

**Переход:** быстрые проверки, диагностика, совместимость основной Qwen, местные контейнеры и исходный дефект дают ожидаемые результаты.

### [Часть 1. Программирующий агент и цикл ReAct](01-программирующий-агент.md)

**С чего начинаем:** среда проверена, общий `Agent` и `CodeAgent` содержат TODO.

**Что делаем:** строим рабочую историю, `build_prompt`, общий цикл ReAct, `execute`, `send_message`, исправимые ошибки и поэтапное раскрытие навыков. Затем `CodeAgent` работает в чистом `/testbed` и создаёт там `patch.txt`; командный интерфейс переносит его на Windows под указанным именем, обычно `artifacts/fix.patch`. Полученный патч независимо проверяется в новом контейнере.

**Зачем перед остальными:** и сжатие, и `ChessAgent` должны использовать один уже проверенный общий цикл.

**Переход:** договоры части 1 проходят проверки, патч применяется к свежему стенду, целевая и регрессионные проверки успешны, траектория согласуется с патчем.

### [Часть 2. Сжатие контекста](02-сжатие-контекста.md)

**С чего начинаем:** `CodeAgent` уже умеет вести длинный диалог и выполнять инструменты.

**Что делаем:** заменяем старую законченную часть истории краткой рабочей памятью, не меняя исходные системные указания, задачу, свежие полные шаги и журналы API. Сравниваем одну и ту же Qwen со сжатием и без него.

**Зачем после части 1:** нельзя надёжно сокращать историю, пока не определены её структура и границы полного шага.

**Переход:** сжатие действительно уменьшает активный контекст, оба опыта имеют отдельные артефакты, патчи проверены независимо, а выводы опираются на измеренные токены, время, шаги, RAM, VRAM и качество.

### [Часть 3. Шахматный агент](03-шахматный-агент.md)

**С чего начинаем:** общий цикл и сжатие готовы, а `fix.patch` из части 1 позволяет запустить исправленную шахматную службу.

**Что делаем:** добавляем `play_move`, `simulate_move`, `run_python` и шахматный навык; затем проводим опыт 2 × 2 для Qwen/GPT-OSS с показом и без показа `legal_moves`.

**Зачем последней:** часть проверяет перенос общего каркаса в другую предметную область и зависит от исправленной службы.

**Переход:** инструменты не нарушают состояние игры и границу песочницы, четыре запуска имеют раздельные траектории и результаты, а программный опыт подтверждён проверками.

Теория также читается последовательно: [лекция 1 об агентах](../../конспекты/01-что-такое-агенты-и-как-они-работают.md), [лекция 2 об инструментах](../../конспекты/02-использование-инструментов-языковыми-моделями.md), перед частью 2 — [лекция 3 о длинном контексте](../../конспекты/03-работа-агентов-с-длинным-контекстом.md), перед навыками — [лекция 4 о памяти и навыках](../../конспекты/04-память-и-навыки-агентов.md).

К реализации переходите только после критериев готовности части 0. Не перескакивайте к шахматным инструментам ради видимого результата: они должны опираться на общий цикл, а не дублировать его.

## 5. Как поручать Cursor одну учебную правку

Исходная точка каждого шага — один TODO или один ясно ограниченный договор. Цель — получить небольшое изменение, которое можно понять и проверить отдельно.

Хорошее узкое поручение должно задать не готовое решение, а пять границ:

1. **Что изучить:** конкретный TODO, относящиеся к нему исходники и открытые тесты.
2. **Какой договор сначала объяснить:** входы, выходы, изменяемое состояние, неизменяемые условия, ошибки и связь с общим циклом.
3. **Что можно менять:** только перечисленные исходники.
4. **Что нельзя менять:** тесты, постановки задач, `chess_app`, `.env`, готовые блоки журналирования и очистки, а также поведение ради обхода проверки.
5. **Как проверить:** сначала узкая проверка, затем соответствующие более широкие ворота и просмотр полученного патча или траектории.

Порядок одного TODO:

1. прочитать условие, заготовку и открытые тесты;
2. своими словами зафиксировать договор поведения;
3. поручить Cursor изучить и изменить только этот участок;
4. до правки получить объяснение затрагиваемых файлов и проверки;
5. после правки просмотреть состав изменений;
6. запустить узкий тест в PowerShell;
7. при отказе передать точный вывод, не разрешая ослаблять тест;
8. запустить более широкие ворота;
9. проверить траекторию, патч и состояние контейнеров;
10. объяснить, почему наблюдения подтверждают результат.

```text
Хорошая граница
один договор → несколько разрешённых файлов → конкретная проверка

Ошибочная граница
«сделай всю часть» → широкие изменения → вывод «всё работает»
```

Патч полезен тем, что показывает точное различие между исходной и изменённой версиями. Но сам патч не доказывает правильность: он должен применяться к чистой исходной точке и проходить независимые тесты.

К следующему TODO переходят только после того, как текущую правку можно объяснить без пересказа ответа Cursor и подтвердить воспроизводимой проверкой.

## 6. Проверочные ворота: от дешёвых к дорогим

Исходная точка — несколько уровней проверки с разной стоимостью и разными причинами отказа. Цель — сначала исключить простые ошибки, а затем расходовать время и память на модель и настоящие контейнеры.

**Все команды этого раздела выполняются пользователем в Windows PowerShell из корня `assignment-1`.** Команды Linux, предложенные `CodeAgent`, сюда не относятся: их выполняет `Environment.execute` внутри контейнера. Точные подготовительные действия и разбор отказов находятся в [части 0](00-обзор-и-подготовка.md).

Начало `uv run` означает: запустить следующую программу в закреплённой среде Python этого проекта. `pytest` находит и выполняет автоматические тесты; каждая проверка сопоставляет наблюдаемое поведение с ожидаемым договором.

### Ворота A. Быстрый инфраструктурный слой

```powershell
uv run pytest tests/test_infrastructure.py tests/test_smoke.py
```

- **Зачем:** проверить настройки и основные договоры без запуска контейнера и без зависимости от TODO.
- **Успех:** проверенный результат — `3 passed`.
- **При отклонении:** остановиться и разобрать инфраструктурную причину по части 0; не менять учебные TODO ради прохождения этого слоя.

## 7. Официальная и местная среда: договор безопасности

Исходная точка — официальное задание рассчитано на внешние службы, а это руководство воспроизводит его поведение на одном компьютере. Цель адаптации — заменить поставщика вычислений, но сохранить архитектуру, учебные TODO и критерии качества.

### Что заменено, а что сохранено

- В официальном курсе песочницу предоставляет Modal; здесь используется Docker Desktop с Linux/amd64 в Hyper-V без WSL.
- Вместо удалённого хранилища используется чистый образ и временный контейнер с тем же `/testbed`.
- Вместо внешней модели `llama-server.exe` работает непосредственно в Windows на `127.0.0.1`.
- `OPENAI_API_KEY=local-dummy` — непустое служебное значение для библиотеки, через которую каркас обращается к API; это не секрет поставщика.
- Вместо публичного или зашифрованного туннеля порт публикуется только на петлевом адресе `127.0.0.1`.
- Официальные имена моделей относятся к первоначальной постановке; местный опыт использует `Qwen3.6-27B-Q6_K` и `gpt-oss-20b-MXFP4`.
- Сдача и оценка курса заменены целью получить воспроизводимые свидетельства и понять архитектуру.

Пакеты `modal` и `swe-rex[modal]` пока остаются в `pyproject.toml`, чтобы не ломать нетронутые исторические проверки. Учётная запись и служба Modal для местного пути не нужны. `assignment-chess-modal` сохранена только как исторический совместимый псевдоним; рабочее имя — `assignment-chess-local`.

### Три договора изоляции

**1. Недоверенный код не исполняется в Windows.**

`execute` должен обращаться к `Environment.execute`, а `run_python` — к контейнерному `/opt/assignment/sandbox_python.py`. В Windows остаются PowerShell пользователя, llama.cpp, клиент API, управляющий каркас и Docker Desktop.

**2. Контейнер не получает лишнего доступа.**

- сеть — `bridge`: контейнер подключён к отдельной виртуальной сети Docker, а не прямо к сети Windows;
- каталоги хоста не подключаются как общие папки (`bind mount`);
- сокет Docker, домашний каталог, `.env` и другие секреты внутрь не передаются;
- устройства, включая GPU, контейнеру не передаются;
- `cap-drop=ALL` убирает дополнительные системные возможности Linux;
- `no-new-privileges` запрещает процессам получать новые повышенные права;
- число процессов ограничено 512;
- доступны не более 8 CPU и 8 GiB RAM; общий предел RAM с подкачкой также равен 8 GiB.

**3. Сеть и время жизни ограничены.**

- `--init` собирает завершившиеся дочерние процессы;
- нужные порты Docker выбирает случайно и связывает только с `127.0.0.1`;
- пользовательские `argv` и `env` обычного `exec` передаются контейнерному исполнителю как JSON через stdin, а не попадают в аргументы `docker.exe`;
- штатный `with`/`finally` немедленно вызывает `stop` и адресное удаление;
- `--rm` выполняет отложенную очистку после `deployment_timeout`, если управляющий процесс оборван и Docker доступен;
- при недоступном или повреждённом Docker сначала сверяется идентификатор контейнера, после чего допустимо только его адресное удаление по процедуре части 0.

### Ресурсный договор

Проверенный профиль Qwen с контекстом 32768 почти исчерпывает компьютер:

- готовность сервера — 18,75 с;
- полная проверка совместимости — 85,02 с;
- пик VRAM — 23822 MiB из 24455 MiB;
- пик RAM — 65774972928 байт.

Проверенная GPT-OSS заметно легче:

- готовность — 8,55 с;
- проверка — 6,44 с;
- пик VRAM — 13250 MiB;
- пик RAM — 56598880256 байт.

Практический порядок:

1. держать загруженной только одну модель;
2. закрыть тяжёлые программы перед одновременной работой модели и Docker;
3. проверить свободные RAM и VRAM перед полным опытом;
4. не запускать несколько агентных опытов параллельно;
5. при нехватке памяти сначала уменьшить контекст модели, затем заново выполнить диагностику, проверку совместимости и сам опыт;
6. записать новое значение контекста как отдельный профиль;
7. не обещать работу с 64K или 128K без отдельного измерения совместимости и пиков памяти.

К опытам можно переходить, если вы можете показать, что сервер доступен только локально, недоверенный код уходит в контейнер, секреты туда не подключены, а выбранный профиль помещается в память.

## 8. Артефакты как доказательства

Исходная точка — агент может уверенно сообщить об успехе даже при неприменимом патче, неполной партии или неверной среде. Цель — заменить доверие к сообщению набором воспроизводимых свидетельств.

Официальный перечень полезен как карта доказательств:

- `fix.patch` показывает результат работы `CodeAgent`;
- `part1-trajectory.json` показывает путь к этому результату;
- отдельные пары патча и траектории со сжатием и без него позволяют сравнить память;
- четыре пары шахматных траекторий и результатов подтверждают опыт 2 × 2;
- `token-usage-analysis.md` отделяет измерения от объяснения тенденций;
- `observation-experiment.md` фиксирует способ подсчёта и ограничения опыта;
- `part3-python-skill-trajectory.json` подтверждает совместную работу навыка, моделирования, программы и живого хода;
- `AI_USAGE.md` фиксирует, какие ИИ-агенты меняли код или анализировали данные и как проверялся их результат.

Имена местных опытов должны отражать фактические модели. Нельзя переименовывать Qwen в официальную модель курса ради совпадения с первоначальным шаблоном.

Артефакт считается свидетельством только тогда, когда:

- относится к записанным команде, модели и профилю;
- JSON разбирается;
- патч применяется к свежей исходной точке;
- результат подтверждается тестами;
- траектория согласуется с патчем или состоянием партии;
- внутри нет содержимого `.env` и других секретов.

```text
Слабое свидетельство
«агент сообщил, что всё исправил»

Сильное свидетельство
траектория → патч → свежий контейнер → целевой и регрессионные тесты
```

Часть считается завершённой, когда другой запуск может воспроизвести проверку по записанным условиям, а пользователь способен связать вывод тестов с траекторией и полученным результатом.

## 9. Краткий словарь

Исходная точка — термины уже встретились в архитектуре и командах. Цель словаря — дать короткие определения, к которым можно возвращаться во время последовательного прохождения.

- **Каркас агента** — управляющая программа, которая готовит сообщения для модели, хранит состояние, исполняет разрешённые инструменты и возвращает наблюдения.
- **Языковая модель** — программа, которая по входной последовательности предлагает вероятное продолжение; в этом задании она также может предложить структурированные вызовы инструментов.
- **Git** — система учёта версий файлов; здесь она закрепляет исходную точку и показывает состав изменений.
- **Docker** — система создания и запуска изолированных контейнеров из образов.
- **API** — согласованный способ, которым программы обмениваются запросами и ответами; здесь каркас использует OpenAI-совместимый API llama.cpp.
- **ReAct** — цикл, в котором модель получает наблюдение, выбирает действие, видит его результат и продолжает до завершения.
- **Инструмент** — действие с известным именем и схемой аргументов, которое модель может запросить, а каркас — проверить и выполнить.
- **Песочница** — изолированная среда с ограниченными ресурсами и доступом для выполнения недоверенного кода.
- **Образ** — неизменяемый шаблон файловой системы и зависимостей, из которого Docker создаёт контейнеры.
- **Контейнер** — отдельный временный процесс и файловая среда, созданные из образа.
- **Тест** — автоматическая проверка наблюдаемого поведения; успешный тест подтверждает только проверенный им договор, а не всю систему.
- **Патч** — текстовое представление различий между версиями файлов, которое можно применить к чистой исходной точке.
- **Траектория** — сохранённая последовательность взаимодействия агента: запросы, ответы, действия и наблюдения.
- **Артефакт** — файл с результатом или свидетельством опыта: патч, траектория, итог партии либо аналитический отчёт.
- **TODO** — отмеченное в заготовке место, договор которого ещё предстоит реализовать.
- **Навык** — отдельная повторно используемая инструкция, которую агент может раскрыть по имени, когда она нужна.
- **`uv`** — средство управления средой и зависимостями Python-проекта; `uv run` запускает команду в этой среде.

После словаря вернитесь к [части 0](00-обзор-и-подготовка.md). Готовность к началу означает, что вы можете нарисовать общий поток своими словами, назвать границу Windows/контейнера и объяснить назначение первых четырёх ворот.
