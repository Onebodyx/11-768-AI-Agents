## Главное за минуту

- Задание выполняется в отдельном репозитории `cmu-agents/assignment-1`. Папка с этим руководством содержит только учебные материалы.
- Один общий класс `Agent` отвечает за цикл ReAct и рабочую историю. `CodeAgent` и `ChessAgent` добавляют предметные запросы и инструменты.
- LLM не запускает команды и не двигает фигуры сама. Она предлагает структурированные действия; каркас проверяет и передаёт их среде.
- Код и приложения исполняются в удалённых песочницах Modal. Запросы к LLM и работа Modal могут расходовать выданные средства.
- `make test` выполняется локально, быстро и бесплатно. Исходная заготовка намеренно не проходит проверки незаполненных TODO.
- Нельзя менять `tests/`, `tasks/` и `chess_app/`, дублировать общий цикл в подклассах или зашивать ответы конкретных задач.
- `.env` содержит секреты и не должен попадать в Git, журналы, запросы модели или архив для сдачи.
- Итог оценивается не только по коду: обязательны патчи, траектории, результаты опытов, два аналитических файла и `AI_USAGE.md`.

## 1. Архитектура задания

### 1.1. Три слоя

**Большая языковая модель (LLM)** получает последовательность сообщений и описания инструментов. Она возвращает текст, рассуждение и структурированные вызовы. Модель не имеет прямого доступа к терминалу, файлам или шахматному серверу.

**Каркас агента** хранит рабочую историю, строит очередной запрос, вызывает LLM, разбирает её ответ, исполняет инструменты и добавляет результаты как новые наблюдения. Основная реализация находится в `Agent`; предметные подклассы задают доступные действия.

**Среда** содержит реальное состояние задачи. Для программирующего агента это удалённая файловая система и командная оболочка в `/testbed`. Для шахматного агента — сервер с текущей партией и HTTP API.

```text
задача пользователя
        |
        v
каркас Agent ----------------------> LLM API
  |  строит запрос                     |
  |  хранит историю                    | текст и tool_calls
  |  проверяет вызовы                  |
  +<-----------------------------------+
  |
  | допустимое действие
  v
Environment или ChessSandbox
  |
  | результат команды / состояние доски / ошибка
  v
наблюдение role="tool" --> новая итерация
```

Ошибки разных слоёв требуют разных исправлений:

- модель выбрала неправильный инструмент — проблема решения или запроса;
- вызов имеет неверный JSON — проблема вывода, которую каркас должен превратить в наблюдение;
- каркас потерял `tool_call_id` — ошибка протокола;
- внешний API вернул отказ — ошибка среды или аргументов;
- песочница не остановилась — ошибка управления ресурсами.

Если всё называть «ошибкой агента», диагностика быстро станет бессистемной.

### 1.2. Почему общий цикл должен находиться в Agent

`CodeAgent` работает с терминалом, а `ChessAgent` — с шахматным API. Но последовательность верхнего уровня одинакова:

```text
построить запрос
получить действие модели
сохранить ответ
исполнить предметные вызовы
сохранить наблюдения
проверить завершение
повторить
```

Эта последовательность должна быть реализована один раз. Подклассы отвечают за:

- начальные инструкции;
- перечень инструментов;
- правила исполнения конкретного вызова;
- преобразование результата среды в сообщение.

Такое разделение проверяет, действительно ли вы построили каркас, а не два независимых сценария.

## 3. Windows, WSL и командная оболочка

Репозиторий использует `Makefile`, оболочечные команды и Linux-песочницы. На Windows наиболее предсказуемый вариант — WSL 2 с Ubuntu:

1. клонировать репозиторий внутрь файловой системы WSL;
2. установить Git, GNU Make и `uv`;
3. выполнять команды задания в терминале WSL;
4. открывать эту папку из Cursor через поддержку WSL.

Так пути, `make`, переменные среды и многострочные команды будут вести себя ближе к среде авторов курса.

Нативная работа в PowerShell возможна, но потребует GNU Make и иногда изменения формы команд. Не меняйте `Makefile` только ради локальной оболочки, если этого не требует само задание. Для копирования файла окружения:

```powershell
Copy-Item .env.example .env
```

Эквивалент в Linux/WSL:

```bash
cp .env.example .env
```

В руководстве основные команды приводятся в форме из официального репозитория. Для длинных опытов с переменными в PowerShell удобнее передавать значения аргументами `make`, а не использовать Unix-синтаксис `NAME=value \` перед командой.

## 4. Подготовка репозитория

### 4.1. Установка uv

Официальный установщик для PowerShell:

```powershell
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
```

Для Linux и WSL:

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
```

Эти команды загружают сценарий с официального домена Astral. Если политика вашей системы запрещает запуск загруженных сценариев, используйте другой [официальный способ установки](https://docs.astral.sh/uv/getting-started/installation/) и не отключайте защиту без согласования.

Проверьте установку:

```bash
uv --version
```

`uv` управляет проектным окружением `.venv`. Команда `uv sync` приводит его в соответствие с `pyproject.toml` и `uv.lock`, а `uv run` выполняет программу именно в этом окружении. `uv.lock` фиксирует разрешённые версии зависимостей; не редактируйте его вручную.

### 4.2. Получение исходников

Один из понятных вариантов:

```bash
git clone https://github.com/cmu-agents/assignment-1.git
cd assignment-1
make setup
```

`make setup` выполняет три действия:

1. `uv sync` создаёт окружение и устанавливает зафиксированные зависимости;
2. `git submodule update --init` получает шахматное приложение;
3. `make verify-sources` проверяет, что исходная задача находится на ожидаемом коммите.

Если настройка сообщает о неправильном состоянии `chess_app`, не исправляйте приложение вручную. Сначала проверьте подмодуль и состояние Git. Задание намеренно требует, чтобы агент позже создал патч внутри свежей песочницы.

Проект требует Python 3.11 или новее. Основные зависимости включают OpenAI-совместимый клиент, Modal, `httpx`, PyYAML, Jinja2 и средства запуска SWE-bench.

### 4.3. Настройка Modal

После установки зависимостей:

```bash
uv run modal setup
```

Команда выполняет вход в Modal. Не вставляйте полученные учётные данные в запросы модели и не публикуйте их.

Для диагностики активных контейнеров используйте версию Modal из окружения:

```bash
uv run modal container list
```

Если после аварийного запуска контейнер остался активным, остановите именно его штатной командой Modal. Сначала убедитесь, что контейнер действительно относится к вашей работе: не завершайте процессы вслепую.

### 4.4. Настройка доступа к LLM

Создайте `.env` из примера и заполните:

```dotenv
OPENAI_BASE_URL=<совместимый адрес API>
OPENAI_API_KEY=<секретный ключ>
OPENAI_MODEL=deepseek/deepseek-v4-flash-0731
OPENAI_MAX_RETRIES=5
```

Смысл полей:

- `OPENAI_BASE_URL` — адрес поставщика OpenAI-совместимого API;
- `OPENAI_API_KEY` — секрет для доступа;
- `OPENAI_MODEL` — модель по умолчанию;
- `OPENAI_MAX_RETRIES` — число повторов временного сбоя поставщика.

Перед продолжением проверьте:

- `.env` исключён из Git;
- ключ не встречается в исходниках;
- ключ не печатается в диагностике;
- базовый URL относится к выданному поставщику;
- число повторов неотрицательно.

## 5. Первые проверки

### 5.1. make doctor

```bash
make doctor
```

Эта команда проверяет подмодули, вход в Modal и конечную точку модели, не создавая песочницу и не генерируя токены. Она нужна, чтобы отделить ошибку настройки от ошибки вашей реализации.

Успешный `doctor` не доказывает, что агент работает. Он лишь подтверждает готовность внешних зависимостей.

### 5.2. Локальные тесты

```bash
make test
```

Эти тесты:

- быстрые;
- работают без Modal;
- не расходуют средства API;
- намеренно падают на незаполненных TODO.

Сохраните исходный результат. Для каждого падения определите, к какому TODO оно относится. Не стремитесь сделать всё зелёным одной большой правкой: так сложнее понять контракт и найти регрессию.

Открытые тесты разрешено читать. Используйте их как исполняемую спецификацию:

1. выпишите вход;
2. выпишите ожидаемое наблюдаемое поведение;
3. определите инвариант;
4. добавьте собственный соседний случай, которого в тесте нет.

Не изменяйте тест, чтобы он согласился с вашей реализацией.

### 5.3. Интеграционные проверки Modal

```bash
make test-modal
make test-chess-modal
```

Они медленные и платные, потому что создают настоящие песочницы. Запускайте их только после локальных проверок и `make doctor`. На первом этапе они необязательны.

## 7. Жизненный цикл одного запуска

Командная программа:

1. читает задачу и настройки;
2. создаёт удалённую среду;
3. создаёт подходящий подкласс агента;
4. вызывает `agent.run()`;
5. извлекает патч либо состояние партии;
6. записывает артефакты;
7. останавливает среду.

Внутри `Agent.run()` блок `finally` сохраняет траекторию даже после ошибки и останавливает среду при соответствующей настройке. Это предоставленная инфраструктура. Если заменить или обойти её, можно потерять диагностические данные и оставить платную песочницу работающей.

`api_prompts` и `api_responses` предназначены для журналирования фактических обращений. Это не рабочая память агента. Активное состояние должно существовать отдельно, чтобы:

- `build_prompt` мог собрать очередную историю;
- сжатие могло заменить старую часть рабочего контекста;
- журналы сохранили исходные запросы для оценки.

## 8. Бесплатные и платные действия

### Обычно бесплатны

- чтение кода и условия;
- `make setup`, кроме обычного сетевого скачивания;
- `make doctor`, согласно условию не создающий песочницу и не генерирующий токены;
- `make test`;
- локальная проверка JSON, YAML и отчётов;
- просмотр уже сохранённых траекторий.

### Расходуют средства

- `make test-modal`;
- `make test-chess-modal`;
- `make run-code-agent`;
- `make check-part1`;
- `make run-swebench-agent`;
- `make check-swebench`;
- `make run-chess-agent`;
- четыре цели `make run-obs-*`;
- прямой запуск `assignment-play-chess`;
- любой вызов LLM, включая отдельное сжатие контекста.

Обе команды `make check-*` запускают тесты в удалённой среде Modal. Они не обращаются к LLM, но расходуют вычислительные средства Modal. Общая стоимость зависит от числа шагов, длины запросов, выходных токенов, повторов и времени работы песочниц.

Перед платным запуском:

1. выполните `make doctor`;
2. выполните нужные локальные тесты;
3. проверьте пути артефактов;
4. убедитесь, что старый файл не будет перезаписан;
5. проверьте предел шагов и время жизни песочницы;
6. после запуска убедитесь, что среда остановлена.

## 10. Рабочий журнал

Рекомендуется вести собственный краткий журнал вне сдаваемых артефактов:

```text
Дата и коммит:
TODO:
Какой контракт понял:
Что изменил:
Какие тесты запустил:
Что прошло:
Что осталось непонятно:
Был ли запуск платным:
Какие файлы созданы:
```

Он помогает не перепутать собственный вывод с наблюдаемым фактом. Например:

- «агент сделал меньше шагов» — факт из траектории;
- «сжатие всегда уменьшает число шагов» — неподтверждённое обобщение;
- «патч проходит открытый тест» — факт;
- «патч полностью правильный» — вывод, который закрытые тесты ещё могут опровергнуть.

## 11. Критерии готовности к части 1

Переходите к реализации, когда:

- репозиторий находится в чистом и понятном состоянии;
- известен текущий коммит;
- подмодуль получен и проверен;
- окружение `uv` создано;
- Modal настроен;
- `.env` заполнен и исключён из Git;
- `make doctor` проходит;
- исходные падения `make test` сохранены и сопоставлены с TODO;
- вы можете объяснить три слоя архитектуры;
- вы знаете, какие файлы разрешено менять;
- вы понимаете, какие команды платные;
- для каждого запуска выбран отдельный путь артефакта.
