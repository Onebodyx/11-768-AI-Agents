## 2. Кто что делает и где проходит граница

### 2.1. Четыре разные роли

Не смешивайте участников:

- **Cursor** изменяет учебный каркас по вашему поручению: читает TODO, объясняет договор и правит разрешённые файлы. Пользователь отдельно запускает и оценивает проверочные команды в PowerShell.
- **`ChessAgent`** общается с местной моделью через OpenAI-совместимый API, передаёт ей наблюдение и исполняет только зарегистрированные вызовы инструментов.
- **`ChessSandbox`** создаёт, настраивает и удаляет контейнер, применяет `fix.patch`, запускает шахматную службу и предоставляет `Environment.execute`.
- **шахматная служба** живёт внутри Linux-контейнера, хранит единственную живую партию и отвечает на HTTP-запросы.

Порождённый моделью Python не является правкой каркаса. Он передаётся через `run_python` доверенному контейнерному исполнителю и выполняется только внутри Linux-контейнера.

### 2.2. Поток данных

```text
Windows
┌──────────────────────────────────────────────────────────────────────┐
│ Cursor                                                              │
│   изменяет разрешённые файлы каркаса                                │
│                                                                      │
│ llama.cpp на 127.0.0.1:8080                                         │
│   ↑↓ OpenAI-совместимые запросы                                     │
│ ChessAgent → общий Agent.run                                        │
│   │                                                                  │
│   ├─ play_move / simulate_move ── HTTP через петлевой порт хоста ─┐ │
│   │                                                               │ │
│   └─ run_python ── _run_python / Environment.execute ─────────────┼─┼─┐
└───────────────────────────────────────────────────────────────────┼─┘ │
                                                                    │   │
Linux-контейнер Docker                                              │   │
┌───────────────────────────────────────────────────────────────────┼───┼─┐
│ шахматная служба на внутреннем порту 8000 ←───────────────────────┘   │ │
│   хранит живое состояние L                                            │ │
│                                                                        │ │
│ /opt/assignment/sandbox_python.py ←────────────────────────────────────┘ │
│   выполняет Python модели                                               │
│   вызывает simulate_move и play_move по 127.0.0.1:8000 внутри контейнера │
│                                                                        │
│ /testbed                                                               │
│   свежая копия приложения + применённый fix.patch                       │
└─────────────────────────────────────────────────────────────────────────┘
```

Случайный опубликованный порт хоста связан только с `127.0.0.1`. Внутри контейнера служба слушает свой внутренний порт. Это разные адреса, хотя они ведут к одной службе.

### 2.3. Что является защитой

- Base64 сохраняет кавычки и переводы строк при передаче кода; это не изоляция и не шифрование.
- Изоляцию даёт Linux-контейнер с ограничениями ресурсов и возможностей.
- Строгая схема уменьшает число неверных вызовов модели; она не доказывает законность шахматного хода.
- Проверка типов защищает границу инструмента; окончательное шахматное решение принимает служба.
- `with`/`finally` обеспечивает немедленную очистку; `--rm` остаётся отложенной страховкой.

**Точка остановки:** если порождённый моделью код направлен в местный `python.exe`, `subprocess`, `eval`, `exec`, `compile` или временный файл Windows, не запускайте его и не продолжайте TODO 3.4.

**Критерий перехода:** вы можете без смешения ролей провести один вызов от модели через `ChessAgent` и `ChessSandbox` до службы или контейнерного исполнителя и обратно.

## 3. `fix.patch` — жёсткие входные ворота

### 3.1. Почему без патча нельзя строить опыт

`ChessAgent` должен играть на исправленной службе. Слова CodeAgent о завершённой работе недостаточны: патч проверяется независимо на свежем стенде. Только после успешной оценки `ChessSandbox` строит новую службу с этим патчем.

```text
CodeAgent
  → /testbed/patch.txt
  → командный интерфейс записывает кандидат на Windows
  → независимая оценка кандидата
  → FAIL_TO_PASS 1/1
  → PASS_TO_PASS 9/9
  → RESOLVED: yes
  → пользователь сохраняет оценённый кандидат как artifacts/fix.patch
  → новая шахматная служба
```

Не раскрывайте в части 3 сам дефект и не переносите исправление в местный `chess_app`. Входом служит доказанный файл `artifacts/fix.patch`.

### 3.2. Независимая оценка

```powershell
uv run python scripts/evaluate.py --task tasks/chess-terminal-move --evaluation tasks/chess-terminal-move/public_tests --patch artifacts/fix.patch -v
```

**Паспорт команды**

- **Среда:** Windows PowerShell.
- **Рабочий каталог:** корень `assignment-1`.
- **Назначение:** применить `fix.patch` к свежему стенду и независимо прогнать регрессионную проверку и прежние проверки приложения.
- **Параметры:** `--task` выбирает закреплённое задание; `--evaluation` — открытый набор оценки; `--patch` — проверяемый вход; `-v` показывает этапы.
- **Ожидаемый признак:** одновременно `FAIL_TO_PASS 1/1`, `PASS_TO_PASS 9/9` и `RESOLVED: yes`; код завершения равен нулю.
- **Смысл отклонения:** `0/1` означает, что требуемый отказ не исправлен; меньше `9/9` означает регрессию; `RESOLVED: no` запрещает шахматный опыт.
- **Точка остановки:** не запускайте `ChessSandbox` с недоказанным патчем и не исправляйте `chess_app` вручную.

**Критерий перехода:** все три ориентира получены в одном свежем запуске, а путь к патчу точно совпадает с последующими командами.

### 3.3. Ручная проверка свежей службы

После зелёной оценки можно отдельно убедиться, что именно этот патч применяется при создании новой службы:

```powershell
$sandboxArgs = @(
  'assignment-chess-local'
  '--task'; 'tasks/chess-terminal-move'
  '--patch'; 'artifacts/fix.patch'
  '--sandbox-timeout'; '1800'
)
uv run @sandboxArgs
```

**Паспорт команды**

- **Среда:** Windows PowerShell; управляющий процесс работает в Windows, служба — в новом Linux-контейнере.
- **Рабочий каталог:** корень `assignment-1`.
- **Назначение:** вручную поднять исправленную службу до подключения модели и увидеть её петлевой URL.
- **Параметры:** `--task` выбирает стенд; `--patch` применяет доказанный вход; `--sandbox-timeout 1800` ограничивает жизнь контейнера 30 минутами.
- **Ожидаемый признак:** напечатан адрес вида `http://127.0.0.1:<случайный-порт>`; после `Ctrl+C` команда завершается штатно.
- **Смысл отклонения:** ошибка применения патча, `/health` или Docker означает, что источник проблемы находится до `ChessAgent`.
- **Точка остановки:** после `Ctrl+C` обязательно выполните проверку контейнеров из раздела 9.6; не запускайте модель, пока список не пуст.

**Критерий перехода:** патч независимо разрешён, новая служба с ним достигает `/health`, а после ручной остановки контейнер удалён.

В терминах задания это слой шахматных инструментов, или `ChessTool`. В текущем каркасе отдельного класса с таким именем нет: его роль выполняют функции `chess_tools.py`. Не создавайте вымышленную параллельную иерархию классов.

### 4.3. `src/assignment/agent/chess_agent.py`

`ChessAgent` связывает общий цикл и предметные инструменты:

- регистрирует только разрешённые на текущем этапе инструменты;
- получает начальное живое состояние;
- строит наблюдение;
- распределяет вызовы;
- связывает каждое наблюдение с исходным `tool_call_id`;
- хранит последний подтверждённый живой снимок в `last_state`;
- устанавливает `finished` только по живой партии.

Он не должен содержать собственный цикл ReAct.

### 4.4. `src/assignment/chess_sandbox.py`

`ChessSandbox`:

- проверяет закреплённый исходник;

- применяет `fix.patch` к `/testbed`;
- запускает шахматную службу;

- выполняет команды через `Environment.execute`;
- закрывает клиент и удаляет контейнер.

Учебные TODO не должны ослаблять этот слой.

### 4.5. `src/assignment/sandbox_python.py`

## 5. Язык состояния игры

### 5.1. Живая доска и снимок

Живая партия принадлежит шахматной службе. Обозначим её текущую позицию как **L**.

`ChessAgent.last_state` — не вторая доска, а последний подтверждённый снимок L. Поэтому после любого действия, которое могло изменить игру, состояние перечитывается у службы.

Основные поля ответа:

- `fen` — компактная запись позиции и служебных прав;
- `squares` — фигуры по клеткам, удобные для печати доски;
- `turn` — чья очередь;
- `legal_moves` — допустимые ходы из этой позиции в UCI;
- `history` — история живой партии;
- `last_move` — последний ход, если служба его возвращает;
- `in_check` — находится ли сторона в шахе;
- `game_over` — закончена ли партия;
- `status` — человекочитаемое состояние.

После успешного живого хода могут также появиться:

- `human_move` — подтверждённый ход белых;
- `engine_move` — автоматический ответ чёрных;
- `human_state` — промежуточное состояние после белых, если оно предусмотрено службой.

`format_chess_state` превращает JSON в тег `<chess_state>` с доской, FEN, очередью, шахом, историей и, в выбранном условии опыта, списком `legal_moves`.

### 5.2. UCI — машинная запись хода

UCI задаёт исходную и конечную клетку:

```text
e2e4
g1f3
e7e8q
```

Последний символ в `e7e8q` обозначает превращение пешки в ферзя. Инструменты принимают UCI, потому что эту форму легко разбирать однозначно.

### 5.3. SAN — запись для человека

SAN описывает шахматный смысл:

```text
e4
Nf3
O-O
```

Один и тот же ход коня может выглядеть как:

```text
UCI: g1f3
SAN: Nf3
```

`play_move` и `simulate_move` ожидают UCI. SAN полезна в `history` для чтения человеком, но `Nf3`, `O-O` или `e4!` нельзя передавать вместо UCI.

### 5.4. FEN — подписанный снимок позиции

Полный FEN содержит шесть полей:

```text
rnbqkbnr/pppppppp/8/8/8/8/PPPPPPPP/RNBQKBNR w KQkq - 0 1
```

Подпись полей:

```text
rnbqkbnr/pppppppp/8/8/8/8/PPPPPPPP/RNBQKBNR | w | KQkq | - | 0 | 1
└──────────── расстановка фигур ─────────────────┘   │      │    │   │   │
                                                     │      │    │   │   └ номер полного хода
                                                     │      │    │   └ счётчик полуходов
                                                     │      │    └ клетка взятия на проходе
                                                     │      └ права рокировки
                                                     └ сторона хода
```

FEN нужен `simulate_move`, чтобы создать отдельную временную доску. Он не заменяет состояние живой службы и не содержит полную историю повторений позиции.

### 5.5. Четыре разных представления

- `squares` отвечает: «что стоит на каждой клетке?»;
- FEN отвечает: «какова позиция вместе с очередью и особыми правами?»;
- UCI отвечает: «какой один ход применить?»;
- SAN отвечает: «как человекочитаемо записать сыгранный ход?».

**Безопасный пример без стратегии:** из начального FEN строка `e2e4` имеет форму UCI; законность всё равно подтверждает служба. Этот пример показывает формат, а не совет по выбору хода.

**Проверка понимания:** объясните, почему одной картинки доски недостаточно для точного моделирования рокировки или взятия на проходе.

## 8. Фаза B — TODO 3.1.b: живой ход

### 8.1. Исходное состояние и цель

Модель уже видит форму `play_move`, но вызов ещё не должен менять партию. Цель — безопасно провести один допустимый вызов до живой службы и вернуть связанное наблюдение.

### 8.2. Успешный поток

```text
assistant.tool_calls[].function.arguments
  → сырая строка JSON
  → json.loads
  → проверка: объект
  → проверка: есть ровно строковый move
  → приведение к договору шахматного инструмента
  → POST /api/move с телом только {"move": ...}
  → проверка HTTP и JSON через шахматный слой
  → подтверждённый ответ службы
  → format_chess_state
  → last_state = живой ответ
  → finished = bool(game_over живого ответа)
  → сообщение role=tool с исходным tool_call_id
```

Под «приведением к договору шахматного инструмента» здесь понимается нормализация через слой `chess_tools.py`: после разбора остаётся только проверенная строка `move`. Это роль `ChessTool` в терминах задания, но отдельного класса с таким именем в местной заготовке нет. Не передавайте серверу весь объект модели и не создавайте параллельную иерархию.

`state` службы — единственный источник истины о живой доске. Нельзя самостоятельно достраивать ответ чёрных, FEN или окончание партии.

### 8.3. Ответ бота

Служба играет за чёрных автоматически после законного хода белых. Один успешный `play_move` обычно возвращает:

- подтверждённый `human_move`;
- `engine_move`;
- новое живое состояние после обоих полуходов;
- следующий список `legal_moves`.

Поэтому отдельный инструмент «сделать ход бота» или «прочитать доску после бота» не нужен.

### 8.4. Исправимые ошибки

Следующие отказы должны стать наблюдением:

```text
<chess_error>понятное описание</chess_error>
```

К ним относятся:

- `arguments` не являются строкой JSON;
- JSON повреждён;
- после разбора получен не объект;
- `move` отсутствует;
- `move` не строка;
- запись хода не соответствует UCI;
- ход незаконен в живой позиции;
- служба вернула HTTP-ошибку;
- произошёл транспортный сбой;
- ответ не JSON;
- JSON-ответ не является объектом;
- вызван неизвестный или незарегистрированный инструмент.

Это исправимые ошибки ReAct: общий цикл не завершается, `finished` не становится истинным, модель получает шанс исправить вызов.

Безопасный пример:

```text
в живой позиции L модель вызвала недопустимый ход
  → служба отвергла его
  → ChessAgent вернул <chess_error>...</chess_error>
  → L и last_state не изменились
  → модель может выбрать другой UCI
```

Не помещайте в сообщение трассировку с секретами и не меняйте ID. Наблюдение должно использовать `tool_call_id` того вызова, который вызвал ошибку.

### 8.5. Несколько `play_move` в одном ответе assistant

Параллельные вызовы полезны для независимых чтений, но живой ход меняет общую доску. Два `play_move` из одного ответа нельзя трактовать как две ветви.

Правило:

1. вызовы рассматриваются как одна группа одного `assistant`;
2. только первый допустимый живой `play_move` может изменить L;
3. каждый следующий `play_move` получает своё отдельное связанное отклонение;
4. лишние вызовы нельзя молча удалять: у каждого исходного `tool_call_id` должен быть ответ `tool`;
5. отклонение дополнительного вызова не завершает общий цикл.

Если более ранний вызов сам неверен, он получает собственный `<chess_error>`. Реализация всё равно обязана гарантировать, что из всей группы не будет подтверждено больше одного живого хода.

### 8.6. Опечатка официального комментария

В комментарии TODO 3.1.b упомянут отсутствующий `fen`. У `play_move` есть только `move`; `fen` относится к `simulate_move`. Не добавляйте вымышленный аргумент ради буквального следования опечатке.

## 11. Фаза E — TODO 3.3: чистое `simulate_move`

### 11.1. Исходное состояние и цель

После опыта 2 × 2 агент умеет только необратимо менять живую партию. Теперь добавляется отдельный инструмент для просмотра позиции и одного воображаемого полухода.

`simulate_move` строит доску из переданного FEN. Он не копирует неявно живую доску и не меняет L.

### 11.2. Договор аргументов

Исполнительный договор:

- `fen` обязателен и является полным шестиполевым FEN;
- `move` может быть строкой UCI, `null` или отсутствовать;
- без хода возвращается разобранная позиция и её допустимые ходы;
- со строкой применяется ровно один полуход за сторону, указанную в FEN.

Для строгих схем OpenAI все объявленные свойства обычно перечисляются в `required`, а необязательность выражается допускаемым `null`. Поэтому различайте:

- **модельную строгую форму:** `move` присутствует, но может быть `null`;
- **устойчивый исполнительный договор:** внутренний вызов без ключа `move` также принимается.

Правильные примеры формы, не полный словарь схемы:

```text
{"fen": "<полный FEN>", "move": null}
{"fen": "<полный FEN>", "move": "g1f3"}
{"fen": "<полный FEN>"}                 # допустимо для исполнительного слоя
```

Недопустимые формы:

```text
{"move": "g1f3"}                        # нет fen
{"fen": "<полный FEN>", "move": 7}      # неверный тип
{"fen": "<полный FEN>", "move": null, "depth": 2}  # лишнее свойство строгой схемы
```

Не вставляйте готовый словарь `SIMULATE_MOVE_TOOL`.

### 11.3. Главный инвариант

```text
живое состояние L
  → simulate_move(fen=A, move=m)
  → временный результат B
  → повторное чтение живой службы
  → живое состояние всё ещё L
```

Короткая запись:

```text
play_move:     L → L'
simulate_move: (L, A) → (L, B)
```

Результат моделирования:

- не записывается в `last_state`;
- не устанавливает `finished`;
- не вызывает автоматический ответ бота;
- не добавляется в историю живой партии;
- может иметь `game_over: true` только для временной ветви.

Если моделирование из FEN, равного L, вернуло B, это не означает, что L стало B.

В `<chess_error>` превращаются:

- повреждённый JSON;
- не-объект;
- отсутствующий `fen`;
- нестроковый `fen`;
- FEN не из шести полей;
- недопустимая позиция;
- `move` неверного типа;
- неверная UCI-запись;
- незаконный ход;
- попытка хода из завершённой позиции;
- транспортный отказ;
- серверная ошибка;
- не-JSON или не-объектный ответ.

Ошибка не должна менять L, `last_state` или `finished`.

## 12. Фаза F — TODO 3.4: `run_python` только в контейнере

### 12.1. Исходное состояние и цель

Отдельные вызовы `simulate_move` позволяют исследовать ветви, но модель должна вручную связывать результаты. `run_python` добавляет программную композицию: один фрагмент может хранить промежуточные FEN и многократно вызывать доступные функции.

Это не разрешение запускать код модели в Windows.

### 12.2. Единственный допустимый маршрут

Требуемую границу удобно записать так:

```text
run_python модели
  → распределитель ChessAgent
  → _run_python(env=ChessSandbox)
  → унаследованный Environment.execute
  → контейнерный sandbox_python.py
```

Отдельного метода `ChessSandbox.run_python` в местной заготовке нет и добавлять его ради этой схемы не нужно.

```text
arguments как строка JSON
  → проверка объекта и строкового code
  → кодирование code в Base64
  → ChessSandbox (env) → Environment.execute
  → внутри Linux-контейнера:
       python /opt/assignment/sandbox_python.py <внутренний-port> <base64-code>
  → JSON {"stdout": ..., "stderr": ..., "error": ...}
  → повторный GET /api/state
  → обновление last_state и finished по живой службе
  → объединённое наблюдение для исходного tool_call_id
```

В каркасе фактический вызов проходит через предоставленный объект среды и `Environment.execute`; не добавляйте локальный `subprocess`.

`<внутренний-port>` — порт службы внутри контейнера, обычно 8000. Это не случайный опубликованный порт Windows.

### 12.3. Base64 — только транспорт

Base64:

- сохраняет переводы строк и кавычки в аргументе команды;
- не делает код безопасным;
- не скрывает содержимое;
- не ограничивает файловую систему или сеть.

Защиту дают контейнер, ограничения ресурсов, отсутствие секретов и сокета Docker, а также фиксированный доверенный исполнитель.

### 12.4. Два разных вида отказа

**1. Ненулевой код контейнерной команды**

```text
Environment.execute.returncode != 0
  → доверенный исполнитель не завершился штатно
  → использовать exception_info или stderr
  → вернуть <chess_error>...</chess_error>
```

Это сбой запуска, тайм-аут, отсутствие файла или другая инфраструктурная ошибка.

**2. Поле `error` в штатном JSON**

```text
returncode == 0
JSON.error не пусто
  → исполнитель отработал
  → исключение возникло в программе модели
  → вернуть штатный JSON со stdout/stderr/error
```

Это не сбой песочницы. Модель должна увидеть своё исключение и исправить программу.

Безопасные примеры формы отказов:

```text
сбой контейнерной команды:
  returncode=1, stderr="..."
  результат инструмента: <chess_error>...</chess_error>

исключение фрагмента:
  returncode=0, stdout='{"stdout":"","stderr":"...","error":"TypeError: ..."}'
  результат инструмента: штатный JSON исполнителя
```

### 12.5. Почему живое состояние перечитывается всегда

Программа могла:

1. успешно вызвать `play_move`;
2. изменить L;
3. затем упасть на следующей строке.

Поэтому после каждого вызова `run_python` нужно попытаться перечитать живую службу независимо от того, вернул фрагмент успешный JSON, поле `error` или ненулевой код контейнерной команды:

- снова запросить `/api/state`;
- заменить `last_state` подтверждённым ответом;
- обновить `finished`;
- добавить форматированное живое состояние к наблюдению.

Если сам контейнер или служба недоступны, перечитать состояние невозможно; это отдельная ошибка среды, которую нельзя маскировать старым `last_state`. Нельзя восстанавливать доску из `stdout`: программа могла ничего не напечатать, напечатать старый FEN или упасть после живого хода.

В процессе Windows-агента запрещены:

- `exec`;
- `compile`;
- `tempfile` с последующим местным запуском;
- `python -c <код модели>`;
- передача модели домашнего каталога, `.env` или сокета Docker.

`exec(compile(...))` внутри `/opt/assignment/sandbox_python.py` является ожидаемой контейнерной реализацией. Запрет относится к Windows-процессу агента.

```powershell
  foreach ($response in @($programmaticTrajectory.responses)) {
    foreach ($choice in @($response.choices)) {
      foreach ($call in @($choice.message.tool_calls)) {
        [pscustomobject]@{
          Name = [string]$call.function.name
          Arguments = [string]$call.function.arguments
        }
      }
    }
  }
)

$invokeIndex = -1
$runPythonIndex = -1
for ($i = 0; $i -lt $calls.Count; $i++) {
  if ($invokeIndex -lt 0 -and $calls[$i].Name -eq 'invoke_skill') {
    $invokeIndex = $i
  }
  if ($invokeIndex -ge 0 -and $calls[$i].Name -eq 'run_python') {
    $runPythonIndex = $i
    break
  }
}
if ($invokeIndex -lt 0 -or $runPythonIndex -le $invokeIndex) {
  throw 'Не найдена последовательность invoke_skill → run_python.'
}

$runArguments = $calls[$runPythonIndex].Arguments | ConvertFrom-Json
$code = [string]$runArguments.code
$simulateCount = [regex]::Matches($code, '\bsimulate_move\s*\(').Count
$playCount = [regex]::Matches($code, '\bplay_move\s*\(').Count
if ($simulateCount -lt 1) {
  throw 'В коде run_python нет вызова simulate_move.'
}
if ($playCount -ne 1) {
  throw "В коде run_python ожидался ровно один play_move; найдено: $playCount."
}

$programmaticResult = Get-Content -Raw -LiteralPath 'artifacts/part3-python-skill-result.json' | ConvertFrom-Json
if ([string]::IsNullOrWhiteSpace([string]$programmaticResult.fen)) {
  throw 'В результате нет подтверждённого живого FEN.'
}
"Программная цепочка подтверждена: simulate_move=$simulateCount, play_move=$playCount."
```

- **Ожидаемый признак:** последняя строка сообщает не менее одного `simulate_move` и ровно один `play_move`.
- **Что проверяется:** порядок `invoke_skill → run_python`, содержимое переданного кода и наличие подтверждённого живого результата.
