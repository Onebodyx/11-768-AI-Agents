## 1. Что строится

`ChessAgent` повторно использует общий цикл `Agent.run` из частей 1–2. Меняется предметный слой:

```text
Agent.run
   |
   +-- запрос к местной модели
   |
   +-- ChessAgent.execute_tool_calls
          |
          +-- play_move
          +-- simulate_move
          +-- run_python
          +-- invoke_skill
```

Если `ChessAgent` создаёт второй цикл ReAct, архитектура неверна. Предел шагов, сжатие, журналирование и очистка должны оставаться общими.

Часть 3 зависит от `artifacts/fix.patch`, созданного в части 1:

```text
CodeAgent
  → fix.patch
  → свежий /testbed
  → исправленная шахматная служба
  → ChessAgent
```

Не заменяйте патч изменением местного `chess_app`.

## 2. Местный ChessSandbox

`ChessSandbox`:

1. проверяет закреплённый исходник;
2. собирает или использует местный образ Linux/amd64;
3. создаёт эфемерный контейнер;
4. копирует доверенные служебные файлы в `/opt/assignment`;
5. применяет `fix.patch` в `/testbed`;
6. запускает шахматную службу внутри контейнера;
7. ждёт успешный `/health`;
8. публикует внутренний порт на случайный порт хоста;
9. связывает его только с `127.0.0.1`;
10. при штатном или обработанном выходе закрывает клиент и немедленно удаляет контейнер; при обрыве процесса `--rm` удаляет его после `deployment_timeout`, если Docker доступен.

Адрес имеет вид:

```text
http://127.0.0.1:<случайный-порт>
```

Это местный HTTP, а не публичный туннель. Не открывайте порт на `0.0.0.0` хоста и не задавайте постоянный наружный порт.

Ручная рабочая точка:

```powershell
$sandboxArgs = @(
  'assignment-chess-local'
  '--task'; 'tasks/chess-terminal-move'
  '--patch'; 'artifacts/fix.patch'
  '--sandbox-timeout'; '1800'
)
uv run @sandboxArgs
```

Остановите её `Ctrl+C`. Проверка очистки:

```powershell
docker ps -a --filter 'label=assignment.local-environment=true'
```

После штатного завершения список должен быть пуст. Если Docker был недоступен или повреждён, восстановите демон, повторите проверку и примените только адресное удаление сверенного контейнера из части 0.

## 3. Где проходит каждое действие

### На Windows

- llama.cpp обслуживает модель на `127.0.0.1:8080`;
- каркас вызывает API;
- пользователь запускает PowerShell;
- записываются траектории и результаты;
- Docker Desktop управляет контейнером.

### В контейнере

- живёт `/testbed`;
- запущена шахматная служба;
- исполняется `/opt/assignment/sandbox_python.py`;
- выполняется любой Python, созданный моделью;
- функции программы обращаются к внутреннему порту службы.

`run_python` никогда не вызывает `exec`, `eval`, `compile` или местный интерпретатор в процессе Windows-агента.

## 4. Файлы и ответственность

### `src/assignment/agent/tools.py`

Содержит описания модельных инструментов:

- `PLAY_MOVE_TOOL`;
- `SIMULATE_MOVE_TOOL`;
- `RUN_PYTHON_TOOL`;
- готовый общий `INVOKE_SKILL_TOOL`.

Описание для модели и исполняющая функция — разные слои.

### `src/assignment/agent/chess_tools.py`

Низкоуровневые действия:

- `_play_move`;
- `_simulate_move`;
- `_run_python`;
- `_invoke_skill`;
- `_game_state`;
- `_request_state`.

HTTP-клиент передаётся явно, чтобы тот же предметный код можно было использовать рядом с сервером внутри контейнера.

### `src/assignment/agent/chess_agent.py`

Связующий слой:

- регистрирует разрешённые инструменты;
- получает начальное живое состояние;
- формирует наблюдение;
- распределяет вызовы;
- сохраняет `last_state`;
- устанавливает `finished` только по живой партии;
- возвращает связанное сообщение `tool`.

### `src/assignment/chess_sandbox.py`

Предоставленная местная инфраструктура Docker. Учебные TODO не должны ослаблять её изоляцию.

### `src/assignment/sandbox_python.py`

Доверенный контейнерный исполнитель. Он предоставляет порождённой программе синхронные `simulate_move` и `play_move`, перехватывает вывод и исключения и возвращает один JSON-объект.

### Запрещённые изменения

Не меняйте:

- `tests/`;
- `tasks/`;
- `chess_app/`;
- Docker-ограничения ради прохождения теста;
- `sandbox_python.py`, если TODO прямо этого не требует;
- общий цикл в отдельную шахматную копию.

## 5. Состояние игры

Живая партия принадлежит серверу. `last_state` — только последний подтверждённый снимок.

Основные поля:

- `fen`;
- `squares`;
- `turn`;
- `legal_moves`;
- `history`;
- `last_move`;
- `in_check`;
- `game_over`;
- `status`.

У успешного живого хода также могут быть:

- `human_move`;
- `engine_move`;
- `human_state`.

`format_state` превращает JSON в тегированное наблюдение с доской, FEN, очередью, шахом, историей и, в соответствующем условии, списком допустимых ходов.

### UCI

Инструменты принимают UCI:

```text
e2e4
g1f3
e7e8q
```

Это не SAN. Нельзя передавать `Nf3`, `O-O` или пояснение рядом с ходом.

### FEN

Для моделирования нужен полный шестиполевой FEN:

```text
rnbqkbnr/pppppppp/8/8/8/8/PPPPPPPP/RNBQKBNR w KQkq - 0 1
```

Поля описывают:

1. расстановку;
2. сторону хода;
3. права рокировки;
4. взятие на проходе;
5. счётчик полуходов;
6. номер полного хода.

Даже полный FEN не содержит историю повторений позиции.

## 7. TODO 3.1.b — живой ход

Путь данных:

```text
сырая строка arguments
  → разбор JSON
  → объект
  → проверка move
  → POST /api/move
  → проверка HTTP и JSON
  → сериализованное состояние
  → format_state
```

В HTTP-тело передаётся только проверенный `move`, а не весь объект модели.

### Исправимые ошибки

В `<chess_error>...</chess_error>` превращаются:

- повреждённый JSON;
- значение не в форме объекта;
- отсутствующий `move`;
- `move` не строка;
- неверная запись;
- незаконный ход;
- отказ HTTP;
- транспортный сбой;
- не-JSON или не-объектный ответ.

Ошибка хода не завершает общий цикл.

### Успешное обновление

После подтверждённого живого хода предметный слой:

- форматирует состояние;
- записывает его в `last_state`;
- устанавливает `finished` по живому `game_over`;
- связывает наблюдение с исходным `tool_call_id`.

### Несколько живых ходов в одном ответе

`play_move` меняет общую доску. Два вызова из одного ответа нельзя считать двумя вариантами из одной позиции. Исполняется не более одного; каждый дополнительный вызов получает собственную восстанавливаемую ошибку.

Молчаливо удалять лишний вызов нельзя: протокол останется с вызовом без результата.

### Уточнение закреплённого условия

В TODO 3.1.b официального текста ошибочно упомянута проверка `fen`. У `play_move` есть только `move`; `fen` относится к `simulate_move`. Не добавляйте вымышленный аргумент ради буквального следования опечатке.

### Маленькое поручение

```text
Изучи TODO 3.1.b, _request_state, ChessAgent.execute_tool_calls и проверки
живого хода. До правки перечисли успешный путь, восстанавливаемые ошибки,
правило нескольких play_move и четыре обновления состояния. Реализуй только
_play_move, регистрацию play_move и соответствующую ветвь диспетчера.
Каждый вызов должен получить свой tool_call_id. Не создавай второй цикл и не
исполняй ничего непосредственно в Windows.
```

## 14. TODO 3.3 — `simulate_move`

### Договор

Операция принимает:

- обязательный полный `fen`;
- `move` как строку UCI, `null` или отсутствие на исполнительном уровне.

Строгая модельная схема должна согласоваться с правилами OpenAI для перечисленных полей; смысл «без хода» выражается допустимым `null`. Исполнитель остаётся устойчивым к допустимому серверному вызову без `move`.

Маршрут:

```text
POST /api/simulate
  → новая временная доска из FEN
  → ноль или один полуход
  → JSON временной позиции
```

### Главный инвариант

Моделирование не меняет живую партию:

```text
live FEN L
  → simulate(FEN A, move)
  → simulated FEN B
  → GET /api/state
  → всё ещё live FEN L
```

Поэтому результат моделирования:

- не записывается в `last_state`;
- не устанавливает `finished`;
- не получает автоматический ответ соперника;
- может завершить только воображаемую ветвь.

### Ошибки

Восстанавливаемо обрабатываются:

- повреждённый JSON;
- не-объект;
- отсутствующий или нестроковый FEN;
- неверное число полей FEN;
- недопустимая позиция;
- `move` неверного типа;
- незаконный ход;
- ход из завершённой позиции;
- транспортный или серверный отказ.

### Маленькое поручение

```text
Изучи TODO 3.3.a/b, маршрут /api/simulate и проверки отсутствия побочного
эффекта. До правки объясни различие строгой модельной схемы и исполнительного
договора, а также почему simulated game_over не завершает живого агента.
Реализуй только SIMULATE_MOVE_TOOL, _simulate_move, условную регистрацию и
ветвь диспетчера. Не меняй last_state или finished по временному результату.
После правки докажи сравнением /api/state до и после, что живой FEN неизменен.
```

## 15. TODO 3.4 — `run_python`

### Назначение

Один фрагмент Python может:

- хранить промежуточные FEN;
- перебирать варианты;
- вызывать `simulate_move`;
- сравнивать результаты;
- один раз вызвать `play_move` для фиксации выбранного хода.

Это программная композиция инструментов, а не разрешение модели исполнять код на Windows.

### Единственный допустимый путь

```text
строка code от модели
  → проверка аргументов
  → Base64
  → Environment.execute
  → python /opt/assignment/sandbox_python.py <internal-port> <base64-code>
  → JSON stdout/stderr/error
```

Base64 защищает передачу кавычек и переводов строк, но не является песочницей и не шифрует код. Защиту даёт контейнер.

Порт здесь — внутренний порт шахматной службы в контейнере. Это не случайный наружный порт Windows.

### Два вида отказа

```text
returncode != 0
  → не сработал контейнерный исполнитель
  → <chess_error>

returncode == 0 и JSON.error заполнен
  → исполнитель сработал
  → исключение возникло в программе модели
  → вернуть штатный JSON
```

Нельзя смешивать эти случаи.

### Повторное чтение живой доски

Программа могла сделать живой ход до исключения. После каждого штатного запуска исполнителя нужно:

- снова запросить `/api/state`;
- обновить `last_state`;
- обновить `finished`;
- добавить форматированное живое состояние к наблюдению.

Нельзя пытаться восстановить живое состояние из `stdout`.

### Маленькое поручение

```text
Изучи TODO 3.4, sandbox_python.py, Environment.execute и проверки программного
инструмента. До правки объясни границу Windows/контейнер, назначение Base64,
различие двух видов отказа и необходимость повторного чтения живой доски.
Реализуй только RUN_PYTHON_TOOL, _run_python, его регистрацию в режиме
programmatic_tools и ветвь диспетчера. Запрещены локальные exec, eval, compile
и subprocess для модельного кода. После правки проверь успех, исключение
программы и ненулевой код контейнерной команды раздельно.
```

## 16. TODO 3.5 — шахматный навык

`tasks/chess-skills/select-move/SKILL.md` использует загрузчик из части 1.

Поэтапное раскрытие:

```text
начальный system:
  name + description

invoke_skill:
  полный SKILL.md как tool
```

`invoke_skill` регистрируется только при непустом допустимом каталоге. Неизвестное имя и повреждённые аргументы становятся `<chess_error>`.

Требуемая связка в траектории:

```text
invoke_skill
  → run_python
      → один или несколько simulate_move для поиска
      → ровно один play_move для живой фиксации
  → перечитанное живое состояние
```

Прямой `play_move` после чтения навыка не доказывает программный поиск. Печать строки хода не меняет доску. Несколько живых ходов внутри программы превращают анализ вариантов в необратимые действия.

### Маленькое поручение

```text
Изучи TODO 3.5, уже реализованный общий загрузчик навыков и проверки
ChessAgent. До правки объясни условную регистрацию invoke_skill и форму
восстанавливаемых ошибок. Реализуй только шахматную обработку invoke_skill,
не создавая второго YAML-загрузчика и не раскрывая полный навык заранее.
После правки проверь отсутствие инструмента без skills_path и возврат полного
content после корректного вызова.
```

## 19. Проверка безопасности `run_python`

Попросите программирующего агента отдельно показать:

- где строка кода кодируется;
- где вызывается `Environment.execute`;
- какой фиксированный контейнерный файл запускается;
- почему наружный порт не передаётся программе;
- почему на Windows нет `exec`, `eval`, `compile` или запуска Python с этой строкой;
- как обрабатывается тайм-аут;
- как после штатного исполнителя перечитывается живая доска.

Проверьте, что контейнер по-прежнему имеет:

- `cap-drop=ALL`;
- `no-new-privileges`;
- `--init`;
- `--rm`;
- 8 CPU;
- 8 GiB RAM;
- 512 процессов;
- сеть `bridge`;
- отсутствие подключённых каталогов, сокета Docker, секретов и устройств;
- только петлевой опубликованный порт.

Обязательный `with`/`finally` по-прежнему должен немедленно очищать штатный запуск; `--rm` не заменяет этот код. Обычный `exec` передаёт модельные аргументы и `env` JSON-ом через stdin, а не через аргументы `docker.exe` на Windows.

## 21. Типичные ошибки

- `ChessAgent` копирует общий цикл.
- `fix.patch` не проверен на свежем стенде.
- В `play_move` добавлен аргумент `fen`.
- Схема допускает лишние свойства.
- Исполнитель использует `arguments` как готовый словарь.
- В HTTP пересылается непроверенный объект модели.
- Незаконный ход завершает весь запуск.
- Наблюдение получает новый ID.
- Все параллельные живые ходы исполняются.
- Лишние вызовы молча исчезают.
- Результат `simulate_move` записывается в `last_state`.
- Воображаемый `game_over` устанавливает `finished`.
- Сокращённый FEN принимается как полный.
- Моделирование вызывает автоматический ответ чёрных.
- Модельный Python исполняется в Windows.
- Base64 ошибочно считается изоляцией.
- Ненулевой код контейнерной команды смешивается с исключением программы.
- После `run_python` живая доска не перечитывается.
- Навык регистрируется при пустом каталоге.
- Полный навык виден в начальном запросе.
- Программа делает несколько живых ходов при поиске.
- Четыре условия используют разные патчи или пределы.
- Qwen и GPT-OSS запущены одновременно.
- Все ошибки считаются незаконными ходами.
- Один файл перезаписывается несколькими партиями.
- Результаты опыта придуманы до запуска.

## 22. Критерии готовности

Часть 3 завершена, если:

- используется общий `Agent.run`;
- `fix.patch` даёт `RESOLVED: yes` на свежем стенде;
- `play_move` имеет строгий договор;
- исполняется не более одного живого хода из группы;
- ошибки возвращаются как связанные наблюдения;
- успешный ход обновляет живое состояние;
- четыре условия Qwen/GPT-OSS × legal on/off сохранены отдельно;
- ограничение GPT-OSS описано честно;
- отчёт использует только фактические числа;
- `simulate_move` не меняет живую доску;
- `run_python` выполняется только через контейнерный исполнитель;
- два вида программных ошибок различаются;
- после программы живая доска перечитывается;
- навык раскрывается только после вызова;
- траектория 3.5 показывает всю связку;
- артефакты согласованы;
- контейнеры удалены;
- Qwen и GPT-OSS не загружались одновременно.
