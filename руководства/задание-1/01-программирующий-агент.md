## 1. Исходная точка, результат и порядок работы

Часть 0 уже должна была подтвердить, что Docker Desktop, закреплённые исходники, `.env`, llama.cpp и OpenAI-совместимый API работают. Теперь исходная точка — готовая местная инфраструктура и каркас с незаполненными TODO в общем `Agent` и предметном `CodeAgent`.

К концу части требуется получить не просто зелёные тесты, а доказанную цепочку:

```text
чистая история сообщений
  → запросы CodeAgent
  → общий цикл ReAct
  → execute и send_message
  → загрузка и раскрытие навыков
  → узкие проверки каждого договора
  → настоящий запуск Qwen
  → непустой патч и траектория
  → независимая оценка в свежем контейнере
```

Порядок зависимостей обязателен:

1. **TODO 1.1.a:** состояние и `build_prompt`;
2. **TODO 1.1.b:** `system_prompt` и `task_prompt` для `CodeAgent`;
3. **TODO 1.2:** общий цикл ReAct;
4. **TODO 1.3:** `execute` и `send_message`;
5. **TODO 1.4:** навыки и `invoke_skill`;
6. узкие и общие проверки;
7. настоящий запуск `CodeAgent`;
8. независимая оценка патча;
9. проверка траектории и очистки.

Следующий этап опирается на предыдущий. Например, диспетчер инструментов — код, который по имени вызова выбирает разрешённый обработчик, — нельзя надёжно проверять, пока активная история теряет вызовы. Настоящий запуск тоже не имеет смысла, пока узкие договоры красные.

**Критерий перехода:** вы можете назвать результат каждого из девяти этапов и объяснить, почему перестановка этапов затруднит поиск причины отказа.

## 2. Четыре роли и граница исполнения

README уже объяснил общую схему. Здесь достаточно зафиксировать различия, которые будут важны при реализации.

- **Программирующий агент Cursor** читает и изменяет каркас в рабочей копии Windows. Именно ему пользователь даёт узкие поручения по TODO.
- **`Agent` и `CodeAgent`** — Python-код этого каркаса. `Agent` отвечает за общий цикл, а `CodeAgent` — за программную задачу и её инструменты.
- **Qwen3.6-27B** работает через llama.cpp по адресу `http://127.0.0.1:8080/v1`. Модель предлагает ответ `assistant`, включая `tool_calls`, но сама не выполняет команды и не меняет файлы.
- **`Environment`** проверенно передаёт разрешённые команды во временный Linux-контейнер Docker. В нём находится `/testbed`, меняются файлы задачи и создаётся `patch.txt`.

```text
пользователь
  → поручает Cursor изменить каркас
  → запускает каркас из Windows PowerShell

каркас Agent/CodeAgent
  → отправляет сообщения Qwen через API
  ← получает assistant с возможными tool_calls
  → проверяет вызовы
  → передаёт execute в Environment

Environment
  → исполняет команду в Linux-контейнере
  ← возвращает код выхода и вывод

каркас
  → превращает результат в сообщение tool для Qwen
```

Порождённая моделью команда никогда не исполняется непосредственно в Windows. В Windows работают доверенные PowerShell-команды пользователя, llama.cpp, управляющий Python-код и Docker Desktop; недоверенные действия модели уходят через `Environment.execute` в контейнер.

**Критерий перехода:** вы можете ответить, кто меняет `base.py`, кто предлагает `tool_calls`, кто исполняет команду и где физически находится `/testbed`.

## 3. Сообщения и один полный шаг ReAct

Запрос к модели — упорядоченный список сообщений. Поле `role` определяет, кто внёс сообщение и как его следует понимать.

### 3.1. Роли сообщений

- **`system`** — постоянные правила, роль агента, сведения о среде и доступные навыки. Обычно это первое сообщение.
- **`user`** — исходная задача или короткое последующее указание продолжить. Постановка задачи идёт после `system`.
- **`assistant`** — полный ответ модели: текст, служебные поля рассуждения и список `tool_calls`, если он есть.
- **`tool`** — наблюдение каркаса после исполнения одного конкретного вызова. Поле `tool_call_id` связывает наблюдение с исходным вызовом.

Модель не создаёт сообщение `tool`: его создаёт каркас после проверки и исполнения действия.

### 3.2. Полный ReAct-шаг

Один шаг состоит не только из запроса к модели:

```text
1. Каркас собирает system + user + активную историю.
2. Модель возвращает один assistant.
3. Каркас сохраняет assistant целиком.
4. Каркас проверяет каждый tool_call.
5. Разрешённое действие исполняется в предметной среде.
6. Для каждого вызова создаётся отдельное наблюдение tool.
7. Наблюдения добавляются в активную историю.
8. Следующий запрос получает весь законченный шаг.
```

Без пункта 6 модель не увидит результат действия. Если сохранить только текст `assistant`, следующий запрос потеряет само действие и связь с наблюдением.

### 3.3. Безопасный игрушечный пример одного вызова

Ниже показана форма сообщений, а не код реализации. Условный инструмент только читает температуру из учебного датчика и ничего не меняет.

```json
{
  "role": "assistant",
  "content": "Сначала узнаю текущее показание.",
  "tool_calls": [
    {
      "id": "call_temp_1",
      "type": "function",
      "function": {
        "name": "read_temperature",
        "arguments": "{\"sensor\":\"classroom\"}"
      }
    }
  ]
}
```

После исполнения каркас добавляет **отдельное** сообщение:

```json
{
  "role": "tool",
  "tool_call_id": "call_temp_1",
  "content": "{\"celsius\":21.4}"
}
```

Пара `assistant → tool` образует законченное действие с наблюдением. В следующий запрос входят оба сообщения в этом порядке.

### 3.4. Два вызова A/B и два связанных наблюдения

Один ответ модели может содержать несколько вызовов. Их нельзя объединять в одно наблюдение:

```text
assistant
  tool_calls:
    A: read_temperature({"sensor": "classroom"})
    B: read_temperature({"sensor": "hall"})

tool(tool_call_id=A, content={"celsius": 21.4})
tool(tool_call_id=B, content={"celsius": 19.8})
```

Связь устанавливается в пределах этого `assistant`. Поставщик API вправе повторить строку ID на более позднем шаге, поэтому глобальный словарь по `tool_call_id` ненадёжен.

Qwen в проверенном местном профиле умеет возвращать два вызова в одном ответе. Каркас всё равно должен обрабатывать список любой допустимой длины.

**Проверка понимания:** если в одном `assistant` есть A и B, следующий запрос обязан содержать сам `assistant`, затем отдельное наблюдение A и отдельное наблюдение B. Только после этого допустим новый запрос к модели.

## 4. Рабочая память агента и журнал запросов

Здесь важно разделить две разные задачи:

1. **Продолжить диалог с моделью.** Для этого агенту нужна рабочая память: какие ответы уже дала модель и что вернули вызванные инструменты.
2. **Сохранить ход выполнения для последующего разбора.** Для этого нужен журнал: какие полные запросы были отправлены и какие ответы пришли от API.

Журнал нельзя использовать вместо рабочей памяти. Он хранит снимки уже состоявшихся обменов, а рабочая память содержит только сообщения, необходимые для следующего запроса.

### 4.1. Из чего строится следующий запрос

У следующего запроса есть две части.

Первая часть постоянна в течение запуска:

```text
system       — постоянные указания агенту
user(task)   — исходная задача
```

Вторая часть растёт после каждого шага. Это **активная история**:

```text
assistant    — ответ модели, включая вызовы инструментов
tool         — результат каждого вызова
user         — короткое указание продолжить, если оно понадобилось
```

Следующий запрос собирается по простой формуле:

```text
следующий запрос
  = system
  + user(task)
  + активная история
```

Например, сначала активная история пуста:

```text
первый запрос:
  system
  user(task)
```

Модель запросила инструмент `A`, а инструмент вернул результат. Агент добавляет в активную историю оба сообщения:

```text
активная история:
  assistant_1(tool_call=A)
  tool(A)
```

Поэтому второй запрос выглядит так:

```text
второй запрос:
  system
  user(task)
  assistant_1(tool_call=A)
  tool(A)
```

Если во втором ответе модель вызвала инструменты `B` и `C`, после их выполнения активная история станет такой:

```text
assistant_1(tool_call=A)
tool(A)
assistant_2(tool_calls=[B, C])
tool(B)
tool(C)
```

Каждое сообщение хранится в ней один раз и в том порядке, в котором возникло.

### 4.2. Что именно хранится в журналах

Поля заготовки имеют следующие назначения:

- **`api_prompts`** — снимки полных запросов, уже отправленных модели;
- **`api_responses`** — полные ответы API в виде данных, пригодных для записи в JSON;
- **`compaction_events`** — сведения о будущих операциях сжатия контекста; в части 1 список обычно остаётся пустым;
- **`steps_taken`** — число успешно полученных ответов модели;
- **`finished`** — признак того, что предметная задача завершена.

После двух запросов журнал `api_prompts` содержит два самостоятельных снимка:

```text
api_prompts[0]:
  system
  user(task)

api_prompts[1]:
  system
  user(task)
  assistant_1(tool_call=A)
  tool(A)
```

Второй снимок уже содержит весь контекст, отправленный во втором запросе. Чтобы построить третий запрос, нельзя склеивать `api_prompts[0]` и `api_prompts[1]`. Иначе начальные сообщения и часть истории повторятся:

```text
неправильно:
  system
  user(task)
  system
  user(task)
  assistant_1(tool_call=A)
  tool(A)
```

Правило можно сформулировать так:

- активная история служит для построения будущего запроса;
- `api_prompts` и `api_responses` служат только для записи уже состоявшихся запросов и ответов;
- `process_response()` извлекает из полного ответа API обычное сообщение `assistant`, которое можно добавить в активную историю.

### 4.3. Почему недостаточно создать новый список

Сообщение — это не просто строка, а словарь, внутри которого могут находиться другие списки и словари, например `tool_calls`.

Предположим, внутренняя история содержит сообщение:

```text
{
  role: assistant,
  tool_calls: [{id: A, ...}]
}
```

Если `build_prompt()` создаст только новый внешний список, вложенный словарь `tool_calls` всё ещё может быть общим с внутренним состоянием агента. Тогда вызывающий код сможет изменить возвращённый запрос — и случайно изменить саму историю.

Поэтому `build_prompt()` должен возвращать **глубокую копию**: независимыми должны быть и внешний список, и все вложенные объекты.

Из этого следуют требования к методу:

1. `build_prompt()` только читает состояние и ничего в него не дописывает.
2. Два вызова подряд без новых действий дают одинаковые по содержанию результаты.
3. Каждый вызов возвращает новую независимую структуру.
4. Изменение возвращённого списка, словаря или `tool_calls` не меняет состояние агента.
5. `api_prompts`, `api_responses` и `compaction_events` не участвуют в построении активной истории.
6. Общий класс работает с ролями сообщений, но не знает имён предметных инструментов.

**Критерий перехода:** вы можете отдельно показать:

1. постоянные `system` и `user(task)`;
2. текущую активную историю;
3. несколько независимых снимков в `api_prompts`.

При этом следующий запрос строится из первых двух частей, а не из журнала.

## 6. TODO 1.1.a — состояние и чистый `build_prompt`

### Что уже есть и чего не хватает

`Agent` уже хранит `system_prompt`, `task_prompt`, журналы API, инструменты и счётчики. Не хватает отдельного состояния активного диалога и чистой сборки следующего запроса.

Желаемое поведение описывается формой, но не телом метода:

```text
новая независимая структура
  = system
  + user(task)
  + активная история в исходном порядке
```

### Почему чистота важна

`build_prompt()` вызывается не только перед API-запросом. Оценка размера контекста, сжатие и тесты тоже могут вызывать его повторно. Если метод при чтении дописывает начальные сообщения или историю, простой подсчёт токенов меняет поведение агента.

Защита нужна на двух уровнях:

- новый список не должен быть общей ссылкой на внутренний список;
- вложенные словари и списки сообщений также не должны позволять внешней мутации состояния.

### Требования к самостоятельно составляемому поручению Cursor

Поручение должно содержать пять частей:

1. **Изучить:** официальный TODO 1.1.a, инициализацию `Agent`, `build_prompt()`, `query_language_model()` и относящиеся проверки `tests/test_agent.py`.
2. **Объяснить до правки:** где будет жить только активная история; почему журналы API для этого не подходят; что означает чистота; как обнаруживается общая ссылка на вложенный словарь.
3. **Изменить:** только состояние части 1.1.a и сборку предметно-независимого запроса.
4. **Не менять:** другие TODO, предметные инструменты, тесты, инфраструктуру и `finally`.
5. **Проверить:** первый запрос, повторный вызов, добавление одного законченного шага и устойчивость к мутации возвращённого значения.

Это перечень требований, а не готовое сообщение для копирования.

### Узкая проверка и переход

Узкая проверка должна подтвердить:

- первый запрос содержит ровно один `system` и одну исходную задачу `user`;
- следующий запрос содержит сохранённый `assistant` и все связанные `tool`;
- повторный вызов не увеличивает историю;
- изменение возвращённой структуры не меняет внутреннее состояние;
- в общем классе нет логики `execute`, шахмат или навыков.

Падения проверок TODO 1.1.b–1.4 на этом этапе допустимы. Падение проверки чистоты или истории текущего TODO — точка остановки.

**Проверка понимания:** объясните, почему выражение «возвращается новый список» ещё не доказывает отсутствие общих ссылок. Переходите дальше, когда узкие проверки 1.1.a зелёные и состав правки ограничен этим договором.

## 7. TODO 1.1.b — запросы `CodeAgent`

### Два запроса с разными обязанностями

После 1.1.a общий `Agent` умеет собирать сообщения, но `CodeAgent` ещё должен определить их исходное содержание.

- `system_prompt` задаёт устойчивую роль `CodeAgent` как агента для программных задач, общий порядок исследования и проверки, фактическую среду и краткий каталог навыков, если они загружены. Это предметная роль запускаемого каркаса, а не программирующий агент Cursor.
- `task_prompt` содержит полную фактическую постановку `task`. Её нельзя заменять кратким пересказом или смешивать с постоянными правилами.

Системные указания должны подходить к разным программным задачам. Они могут требовать сначала исследовать и воспроизвести поведение, затем сделать узкую правку и проверить её, но не могут раскрывать решение текущей задачи.

### Обязательный блок сведений о системе

Официальный договор требует следующую **форму данных**:

```text
<system_information>
{
  "machine": <machine>,
  "release": <release>,
  "system": <system>,
  "version": <version>
}
</system_information>
```

Значения берутся только из:

- `environment.machine`;
- `environment.release`;
- `environment.system`;
- `environment.version`.

Это сведения Linux-контейнера. При создании `Environment` значения получают командой `uname` внутри контейнера; `platform.uname()` управляющей Windows здесь дал бы неверную среду.

Безопасно сериализовать значения означает использовать корректное JSON-представление: строки должны быть заключены в кавычки, а кавычки, обратные косые черты, переводы строк и другие особые символы — экранированы. Простая подстановка произвольного значения между кавычками может создать повреждённый JSON или изменить структуру блока.

Если навыков нет, исходный запрос не должен упоминать `invoke_skill`, `patch.txt` или порядок сдачи. Если навыки есть, здесь размещается только их краткий каталог, а не полное содержимое.

## 8. TODO 1.2 — общий цикл ReAct

### Что связывает цикл

К этому этапу запрос уже можно собрать. Теперь `Agent.run()` должен повторять один и тот же предметно-независимый жизненный цикл для будущих `CodeAgent` и `ChessAgent`.

Правильный порядок удобнее читать как схему:

```text
до запроса:
  1. если finished=True — завершить
  2. если steps_taken >= step_limit — поднять StepLimitError

запрос и ответ:
  3. получить следующий assistant через query_language_model()
  4. сохранить assistant целиком в активной истории

действия:
  5. если есть tool_calls — передать весь список предметному исполнителю
  6. получить по одному tool-наблюдению на каждый вызов
  7. сохранить все наблюдения в порядке вызовов

после действий:
  8. проверить finished
  9. если задача не завершена — начать следующий оборот
```

В заготовке рядом находится отдельный TODO 2.2 про `maybe_compact_context()`. В части 1 его ещё не подключают: сначала нужен доказанный обычный цикл без сжатия. Место вызова и его порядок разбираются в части 2.

### Текст без `tool_calls`

Обычный текст `assistant` не завершает `CodeAgent`. Каркас:

1. сохраняет ответ целиком;
2. добавляет короткое предметно-независимое сообщение `user` с просьбой продолжить допустимым действием;
3. не придумывает вызов за модель;
4. не увеличивает счётчик из-за добавленной реплики.

Завершение предметной задачи наступает только по договору подкласса. Для `CodeAgent` это успешный `send_message`.

### Точная семантика `step_limit`

Один шаг — один успешный запрос действия через `query_language_model()`. Внутренние повторы OpenAI-клиента при временном отказе поставщика не являются новыми шагами каркаса.

- **`step_limit=0`:** модель не вызывается ни разу; сразу возникает `StepLimitError`.
- **`step_limit=1`:** разрешён ровно один запрос. Если его действия завершают задачу, запуск успешен. Иначе действия и наблюдения этого ответа всё равно полностью обрабатываются, а следующая попытка отклоняется до API.
- **`step_limit=N`:** разрешено не более N запросов. N-й ответ сохраняется и исполняется полностью. Запрос N+1 невозможен.

`steps_taken` уже увеличивается внутри `query_language_model()` после успешного ответа. Второе увеличение в `run()` нарушит предел.

### `finished` и неизменяемый `finally`

Общий цикл читает `finished`, а предметный исполнитель устанавливает его по своему договору. Нельзя считать любой текст модели завершением.

Предоставленный `finally`:

- сохраняет траекторию при нормальном завершении и ошибке;
- вызывает `stop()`, если каркас владеет средой;
- должен оставаться неизменным;
- работает вместе с Docker `--rm`, но не заменяется им.

При штатном или обработанном выходе достигнутый `finally` немедленно удаляет контейнер. При аварийном обрыве управляющего процесса `--rm` выполняет отложенную очистку после `deployment_timeout`, если Docker доступен.

1. **Изучить:** TODO 1.2, `query_language_model()`, `execute_tool_calls()`, границу соседнего TODO 2.2 и весь предоставленный `finally`.

## 9. TODO 1.3 — `execute` и `send_message`

### Регистрация без потери существующих инструментов

Базовый `Agent` мог уже зарегистрировать `INVOKE_SKILL_TOOL`. Поэтому `CodeAgent` добавляет, а не заменяет список:

```text
без навыков:
  execute
  send_message

с навыками:
  invoke_skill
  execute
  send_message
```

Схема инструмента — это договор для модели, но не доверенная гарантия. Диспетчер всё равно проверяет фактически полученные данные.

### Независимая обработка каждого вызова

Для каждого вызова по отдельности требуется:

1. сохранить исходный `id`;
2. проверить форму записи вызова;
3. прочитать имя функции;
4. разобрать строку `arguments` как JSON;
5. убедиться, что верхний уровень — объект;
6. проверить обязательные поля, допустимые имена и типы;
7. исполнить только явно известный инструмент;
8. преобразовать результат или ошибку в строковое наблюдение;
9. вернуть одно сообщение `tool` с исходным `tool_call_id`.

Один общий `try` вокруг списка опасен: повреждённый вызов A не должен лишить корректный вызов B его наблюдения.

Безопасная форма исправимой ошибки может выглядеть так:

```json
{
  "role": "tool",
  "tool_call_id": "call_bad",
  "content": "Ошибка аргументов: ожидался JSON-объект."
}
```

Точный текст реализации может отличаться. Существенно, что ошибка является строковым наблюдением, связана с исходным вызовом и позволяет модели исправиться на следующем шаге.

### Договор `execute`

Схема разрешает:

- обязательный `command`: строка либо список строк;
- необязательный `shell`: логическое значение или `null`;
- необязательный `cwd`: строка или `null`;
- необязательный `timeout`: число или `null`;
- необязательный `env`: объект со строковыми значениями или `null`;
- никаких лишних полей.

Аргументы передаются в `Environment.execute`; местный запуск создаёт среду с рабочим каталогом `/testbed`, поэтому он используется по умолчанию.

Каждый вызов работает в новой подоболочке Linux. Обычные `cd` и `export` не сохраняются для следующего вызова; устойчивые `cwd` и переменные передаются соответствующими аргументами. Изменённые файлы контейнера сохраняются между вызовами до удаления самого контейнера.

Ненулевой `returncode` — наблюдение, а не автоматический отказ каркаса. Например, красный целевой тест может быть нужным доказательством воспроизведения. `format_tool_output()` переводит структурированный результат в строку с полями и сокращает слишком длинный вывод, сохраняя начало и конец.

Иллюстративная форма наблюдения:

```text
<exception_info></exception_info>
<output>проверка обнаружила несоответствие</output>
<returncode>1</returncode>
```

Это не команда и не решение задачи.

### Договор `send_message`

`send_message`:

- принимает ровно строковый `summary`;
- при корректном вызове устанавливает `finished=True`;
- возвращает отдельное связанное наблюдение;
- не создаёт `patch.txt` и не доказывает наличие патча.

Если один `assistant` содержит успешный `send_message` и последующие вызовы, среду после завершения менять нельзя. Каждый оставшийся вызов всё равно получает собственное наблюдение об отклонении.

```text
assistant(tool_calls=[A: send_message, B: execute])
tool(A, "завершение принято")
tool(B, "вызов отклонён: агент уже завершён")
```

### Что превращается в наблюдение

- повреждённый JSON;
- JSON-массив, строка, число или `null` вместо объекта;
- отсутствующий обязательный аргумент;
- лишний аргумент;
- неверный тип;
- неизвестное имя инструмента;
- попытка действия после завершения.

Каркас не исправляет JSON, не угадывает пропущенный аргумент и не вызывает произвольный метод через `getattr`.

### Требования к самостоятельно составляемому поручению Cursor

1. **Изучить:** TODO 1.3, `EXECUTE_TOOL`, `SEND_MESSAGE_TOOL`, `Environment.execute()`, `format_tool_output()` и проверки диспетчеризации.
2. **Объяснить до правки:** ветви одного вызова; точную проверку JSON; почему ненулевой код команды не равен отказу каркаса; поведение вызовов после завершения.
3. **Изменить:** регистрацию двух инструментов и предметный диспетчер `CodeAgent`.
4. **Не менять:** общий цикл, инфраструктуру, локальный `subprocess`, тесты и другие TODO.
5. **Проверить:** один вызов; два вызова; повреждённые аргументы; неизвестное имя; ненулевой код; `send_message` перед дополнительным вызовом.

### Узкая проверка и переход

Этап подтверждён, когда каждому исходному вызову соответствует ровно одно строковое наблюдение с тем же ID, корректные команды доходят только до `Environment.execute`, а исправимые ошибки не обрывают весь список.

## 10. TODO 1.4 — навыки и поэтапное раскрытие

### Что такое навык

Навык — отдельная инструкция для повторяемого вида работы. Его каталог сообщает модели, **что доступно**, а полный текст раскрывает, **как действовать**, только когда модель вызывает `invoke_skill`.

Это уменьшает исходный запрос: десятки длинных инструкций не занимают контекст, если они не нужны.

### `metadata` и `content`

Для каждого навыка хранятся два представления:

- `metadata` — краткая строка с `name` и `description` для системного каталога;
- `content` — полный исходный текст соответствующего `SKILL.md`, который возвращается только как наблюдение `invoke_skill`.

Условный игрушечный каталог:

```text
toy-skills/
  inspect-log/
    SKILL.md
```

Начало такого файла концептуально содержит:

```text
---
name: inspect-log
description: Найти в учебном журнале строки с ошибками
---
[дальнейшие учебные шаги здесь намеренно не приведены]
```

Это иллюстрация полей, а не готовый `SKILL.md` для копирования.

YAML-заголовок — блок метаданных между начальной и закрывающей строками `---`. После него находится содержательная инструкция.

### Нерекурсивное обнаружение и строгая проверка

`skills_path` указывает на каталог навыков. Загрузчик рассматривает только его непосредственные дочерние каталоги и ожидает по одному `SKILL.md` в каждом. Вложенные уровни рекурсивно не обходятся: иначе случайный служебный каталог может незаметно стать навыком.

Нужно отклонять ясным `ValueError`:

- отсутствующий путь;
- путь к файлу вместо каталога;
- непосредственный дочерний каталог без `SKILL.md`;
- отсутствующую или незакрытую границу YAML;
- YAML не в форме объекта;
- отсутствующие, пустые или неверно типизированные `name`/`description`;
- одинаковый `name` в разных дочерних каталогах.

Дубликат определяется по полю `name`, а не по имени каталога. Молчаливое перезаписывание сделало бы выбранный навык зависимым от порядка обхода файловой системы.

### Поэтапное раскрытие

```text
до invoke_skill:
  system содержит только metadata всех навыков

assistant вызывает invoke_skill({"name": "inspect-log"})

после invoke_skill:
  tool содержит полный content выбранного навыка
```

Если `skills_path=None` или каталог не дал навыков по разрешённому договору, `invoke_skill` не регистрируется и запрос не раскрывает инструкции о `patch.txt`.

### Требования к самостоятельно составляемому поручению Cursor

1. **Изучить:** TODO 1.4, конструктор `Agent`, схему `INVOKE_SKILL_TOOL`, формат реальных `tasks/code-skills/*/SKILL.md` и относящиеся проверки.
2. **Объяснить до правки:** границу нерекурсивного поиска; YAML-заголовок; различие `metadata`/`content`; опасность дубликатов.
3. **Изменить:** строгую загрузку, краткий каталог в запросе и вызов `invoke_skill`.
4. **Не менять:** полный текст существующего навыка, тесты, задачи, общий цикл и инфраструктуру; не помещать `content` в исходный запрос.
5. **Проверить:** корректный игрушечный каталог, каждый вид повреждения, дубликаты, неизвестное имя и отсутствие навыков.

### Узкая проверка и переход

Этап подтверждён, если исходный запрос показывает только краткие описания, полный текст появляется лишь после связанного вызова, а повреждённый каталог останавливает создание агента понятной ошибкой.

**Проверка понимания:** объясните, почему краткий каталог экономит контекст и почему неизвестное имя при вызове лучше вернуть как восстанавливаемое наблюдение.

## 12. Как настоящий `CodeAgent` работает в `/testbed`

До этого шага проверялась обвязка на управляемых сценариях. Теперь нужно понять ожидаемый инженерный путь без подсказки конкретного шахматного исправления.

### 12.1. Воспроизвести

`CodeAgent`:

- осматривает `/testbed`;
- читает постановку и относящиеся файлы;
- сравнивает описанный сценарий с фактическим поведением;
- запускает узкую проверку;
- сохраняет код выхода и диагностический вывод;
- отделяет наблюдаемый факт от гипотезы.

Ненулевой код на этом шаге может быть правильным свидетельством исходного дефекта.

### 12.2. Исследовать

Агент прослеживает поток данных, ищет место расхождения между постановкой и фактическим поведением и проверяет гипотезы дополнительными наблюдениями. Руководство намеренно не называет точное условие дефекта и строку исправления.

### 12.3. Исправить узко

Правка должна:

- устранять только подтверждённую причину;
- сохранять остальные сценарии;
- не скрывать ошибку общим перехватом;
- не менять тесты;
- не добавлять временные файлы в патч.

### 12.4. Проверить

Нужны четыре группы свидетельств:

- исходный сценарий действительно воспроизводился до правки;
- целевая проверка проходит после правки;
- регрессионные проверки проходят;
- различие Git содержит только относящееся изменение.

### 12.5. Подготовить `patch.txt` через навык

Подробный протокол не встраивается в исходный запрос. Модель видит краткое описание навыка, вызывает `invoke_skill`, получает полное содержимое и только затем подготавливает `patch.txt` внутри контейнера.

Все команды, предложенные Qwen через `execute`, имеют единый паспорт:

- **Среда:** Linux-контейнер Docker, никогда не Windows.
- **Рабочий каталог:** `/testbed`, если вызов явно не передал другой безопасный `cwd`.
- **Назначение:** воспроизведение, исследование, узкая правка или проверка.
- **Смысл результата:** `output`, `returncode` и `exception_info` возвращаются Qwen как наблюдение.
- **Признак успеха:** определяется целью конкретного шага; для воспроизведения ожидаемым может быть ненулевой код, для проверки после правки — нулевой.
- **Отклонение:** ошибка одной команды обычно становится следующим наблюдением; мёртвый контейнер, нарушение границы Windows или невозможность дальнейшего исполнения требуют остановки.

**Проверка понимания:** вы можете объяснить путь «воспроизвести → исследовать → узко исправить → проверить → вызвать навык → создать `patch.txt`», не называя готового исправления.

## 13. Предпусковые ворота

Настоящий запуск дорог по времени и памяти, поэтому перед ним повторно проверяется среда. Все команды раздела выполняются пользователем, а не Qwen.

```powershell
uv run assignment-doctor
uv run python scripts/check_local_model.py
Get-CimInstance Win32_OperatingSystem | Select-Object FreePhysicalMemory
nvidia-smi --query-gpu=memory.total,memory.used,memory.free --format=csv
docker ps -a --filter 'label=assignment.local-environment=true'
```

**Общий паспорт**

- **Среда:** Windows PowerShell.
- **Рабочий каталог:** корень `assignment-1`.

**Назначение и признаки по строкам**

1. `uv run assignment-doctor` проверяет Docker, настройки API, закреплённые исходники и точное имя модели. Успех — завершение без диагностической ошибки. Любая красная проверка — остановка и возврат к части 0.
2. `uv run python scripts/check_local_model.py` проверяет совместимость Qwen с обычным ответом, одним и двумя вызовами инструментов и нужными параметрами API. Успех — полное прохождение для `Qwen3.6-27B-Q6_K`. Отклонение — не запускать агента до восстановления совместимости.
3. `Get-CimInstance ... FreePhysicalMemory` показывает свободную оперативную память Windows. Это измерение, а не тест с одним порогом; подозрительно малый запас при загруженной Qwen означает закрыть тяжёлые программы и повторить измерение.
4. `nvidia-smi ...` показывает общую, занятую и свободную видеопамять. Недостаточный запас или несколько тяжёлых процессов означают остановиться и оставить загруженной одну модель.
5. `docker ps -a ...` ищет контейнеры задания по метке. Успех перед запуском — отсутствие старого контейнера. Найденный оставшийся контейнер — точка остановки и адресная очистка по части 0.

Дополнительно `.env` должен указывать `OPENAI_MODEL=Qwen3.6-27B-Q6_K`, но содержимое `.env` нельзя печатать в отчёт или траекторию.

**Критерий перехода:** диагностика и совместимость зелёные, ресурсов достаточно, Qwen запущена одна и старых контейнеров задания нет.

## 14. Настоящий запуск `CodeAgent`

Запуск создаёт чистый образ задачи, новый контейнер и отдельную пару артефактов попытки.

```powershell
$codeAgentArgs = @(
  'assignment-code-agent'
  '--model'; 'Qwen3.6-27B-Q6_K'
  '--task'; 'tasks/chess-terminal-move'
  '--step-limit'; '200'
  '--skills-path'; 'tasks/code-skills'
  '--trajectory'; 'artifacts/part1-qwen-run-01-trajectory.json'
  '--patch-output'; 'artifacts/part1-qwen-run-01.patch'
)
uv run @codeAgentArgs
```

**Паспорт команды**

- **Среда:** Windows PowerShell; Qwen работает в Windows через llama.cpp, а её `execute`-действия уходят в Linux-контейнер.
- **Рабочий каталог:** корень `assignment-1`.
- **Назначение:** запустить `CodeAgent` с пределом `200`, навыками и уникальными путями артефактов.
- **Смысл результата:** командный интерфейс загружает задачу, создаёт чистый `/testbed`, запускает цикл, после завершения читает `patch.txt`, записывает патч и траекторию в Windows и закрывает контейнер.
- **Признак успеха:** команда завершается с кодом `0`, печатает пути, оба файла существуют, патч непустой, контейнер удалён.
- **Отклонение:** ошибка API, `StepLimitError`, сбой среды или отсутствие артефактов требуют изучить траекторию. Пустой или отсутствующий `patch.txt` — точка остановки, даже если модель вызвала `send_message`.

```text
Task.load
  → проверка закреплённого chess_app
  → чистый местный образ
  → новый Linux-контейнер с /testbed
  → CodeAgent.run
  → patch.txt внутри контейнера
  → чтение patch.txt
  → artifacts/part1-qwen-run-01.patch в Windows
  → удаление контейнера
```

Номер попытки входит в пути. Новый запуск не должен перезаписывать старую траекторию: иначе невозможно связать конкретный патч с породившей его историей.

После выхода повторите последнюю команду проверки контейнеров из раздела 13. Если контейнер остался, остановитесь: наличие патча не отменяет нарушение очистки.

**Критерий перехода:** есть согласованная пара непустого патча и разбираемой траектории одной попытки, а контейнер удалён.

## 15. Независимая оценка патча

Ответ модели и тесты внутри изменённого `/testbed` ещё не доказывают переносимость. Оценка создаёт свежий стенд из закреплённой исходной точки и применяет патч заново.


**Паспорт команды**

- **Среда:** Windows PowerShell, управляющий сценарий создаёт отдельный Linux-контейнер.
- **Рабочий каталог:** корень `assignment-1`.
- **Назначение:** применить патч попытки к чистой копии и запустить целевую и регрессионные проверки.
- **Смысл результата:** `FAIL_TO_PASS` показывает исправление ранее падавшей проверки; `PASS_TO_PASS` — сохранение прежних проходивших сценариев; `RESOLVED` объединяет итог.
- **Признак успеха:** одновременно:

```text
FAIL_TO_PASS 1/1
PASS_TO_PASS 9/9
RESOLVED: yes

```

- **Отклонение:** любая другая строка или ненулевой код означает, что патч не доказан. Это точка остановки: нельзя копировать его под основное имя или переходить к части 2.

```powershell
Copy-Item -LiteralPath 'artifacts/part1-qwen-run-01-trajectory.json' -Destination 'artifacts/part1-trajectory.json'
```

**Паспорт команд**

- **Среда:** Windows PowerShell.
- **Рабочий каталог:** корень `assignment-1`.
- **Назначение:** скопировать именно оценённые патч и траекторию под стабильные имена.
- **Смысл результата:** отсутствие вывода и ошибок обычно означает успешное копирование.
- **Признак успеха:** оба целевых файла существуют и происходят из одной проверенной попытки.
- **Отклонение:** ошибка пути или несогласованная пара — остановка; не подменяйте один файл результатом другой попытки.

Повторно проверьте стабильное имя:

- **Признак успеха:** снова `1/1`, `9/9`, `RESOLVED: yes`, код `0` и отсутствие оставшегося контейнера.
- **Отклонение:** остановка; основная пара артефактов не считается готовой.

**Критерий перехода:** патч дважды применился к свежей исходной точке и оба раза дал точные критерии успеха.

## 16. Проверка траектории

Траектория нужна не для отчётности, а для проверки причинной цепочки. Существование JSON-файла недостаточно.

В `artifacts/part1-trajectory.json` найдите свидетельства:

- первый запрос содержит один `system`, полную задачу и сведения Linux-контейнера;
- активная история не дублирует прежние снимки запросов;
- Qwen вызывает только зарегистрированные инструменты;
- каждый `tool_call` имеет отдельное связанное наблюдение;
- несколько вызовов одного ответа обработаны полностью, если встречались;
- текст без вызова не был принят как завершение;
- `CodeAgent` сначала сравнил постановку с фактическим поведением и воспроизвёл несоответствие;
- гипотезы проверялись действиями, а не объявлялись фактами;
- после правки были целевая и регрессионные проверки;
- полный текст навыка появился только после `invoke_skill`;
- `send_message` произошёл после подготовки непустого патча;
- траектория относится к тому же патчу, который прошёл оценку;
- журнал не содержит `.env`, настоящих секретов или лишних данных пользователя.

Дополнительно проверьте массивы:

```text
prompts      — снимки реально отправленных запросов
responses    — полные ответы API
compactions  — в части 1 обычно пуст; это допустимо
```

Не пытайтесь восстановить активную историю простым склеиванием `prompts`: каждый элемент уже является полным снимком своего шага.

**Критерий перехода:** по траектории можно проследить «наблюдение → гипотеза → действие → результат → проверка → патч», а её содержимое согласуется с оценённым файлом.

## 17. Типичные ошибки и точки остановки

### Ошибки истории и цикла

- активная история строится из `api_prompts` и дублируется;
- `build_prompt()` меняет состояние или возвращает общие вложенные объекты;
- сохраняется только `assistant.content`, а `tool_calls` теряются;
- два вызова получают одно объединённое наблюдение;
- ID считается глобально уникальным;
- текст без инструмента преждевременно завершает запуск;
- предел разрешает запрос N+1;
- `steps_taken` увеличивается второй раз в `run()`;
- TODO 2.2 про `maybe_compact_context()` преждевременно смешивается с реализацией обычного цикла части 1;
- предоставленный `finally` изменён.

### Ошибки инструментов и навыков

- один повреждённый вызов лишает наблюдений остальные;
- ненулевой код теста превращается в фатальное исключение;
- повреждённый JSON автоматически исправляется;
- неизвестное имя исполняется через произвольный `getattr`;
- новый список инструментов затирает `invoke_skill`;
- действие после `send_message` всё же меняет среду;
- навыки ищутся рекурсивно;
- дубликат имени молча перезаписывается;
- полный `SKILL.md` попадает в исходный запрос;
- без навыков запрос раскрывает `patch.txt`.

### Ошибки среды и доказательств

- сведения о системе взяты из Windows;
- `CodeAgent` запускает местный `subprocess` вместо `Environment.execute`;
- исправление внесено прямо в `chess_app`;
- успех объявлен по одному тесту в загрязнённом каталоге;
- патч и траектория относятся к разным попыткам;
- контейнер остался после запуска или оценки.

### Безусловные точки остановки

Остановитесь и не переходите дальше, если:

1. инфраструктурные ворота красные;
2. Cursor изменил запрещённые файлы или предоставленный `finally`;
3. проверка текущего TODO красная;
4. `patch.txt` отсутствует или пуст;
5. патч не даёт `1/1`, `9/9`, `RESOLVED: yes`;
6. контейнер задания остался после штатного выхода;
7. недоверенная команда или порождённый моделью код направлены на исполнение в Windows.

Отказ — это сведения о нарушенном договоре, а не повод расширять область правки. Сначала классифицируйте его как инфраструктуру, текущий TODO, будущий TODO, модель, артефакт или очистку.

**Критерий перехода:** для каждой точки остановки вы знаете, какое доказательство нужно получить повторно и почему нельзя продолжать на предположении.

## 18. Критерии готовности части 1

Часть завершена только при одновременном выполнении всех условий:

- роли Cursor, Qwen, `Agent`/`CodeAgent` и `Environment` не смешиваются;
- `build_prompt()` чист, независим от предметной области и защищён от общих ссылок;
- активная история отделена от `api_prompts`, `api_responses` и `compaction_events`;
- роли и порядок сообщений корректны;
- один и несколько вызовов получают отдельные связанные наблюдения;
- текстовый ответ без вызова не завершает `CodeAgent`;
- предел шагов точен для 0, 1 и N;
- `finally` не изменён и срабатывает при успехе и отказе;
- исправимые ошибки инструментов возвращаются как наблюдения;
- `execute` использует только контейнерный `Environment.execute`;
- сведения системы описывают Linux-контейнер и корректно сериализованы;
- навыки строго проверяются, загружаются нерекурсивно и раскрываются поэтапно;
- узкие проверки текущих TODO зелёные;
- инфраструктура сохраняет результаты `3 passed` и `61 passed`;
- Qwen создаёт непустые патч и траекторию одной попытки;
