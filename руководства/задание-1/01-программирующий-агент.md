## 1. Цель части

Нужно построить общий предметно-независимый каркас ReAct, а затем применить его в `CodeAgent`. Результат считается понятным и проверенным, если:

- запрос содержит устойчивые системные указания, задачу и текущую историю;
- ответ модели сохраняется вместе с вызовами инструментов;
- каждый вызов получает отдельное связанное наблюдение;
- ошибки действия возвращаются модели и не обрывают цикл без необходимости;
- предел шагов не допускает лишнего запроса;
- навыки раскрываются поэтапно;
- CodeAgent исследует чистый `/testbed`, воспроизводит дефект, создаёт и проверяет исправление;
- патч применяется к свежей исходной точке;
- при штатном или обработанном исходе `finally` сохраняет траекторию и немедленно удаляет контейнер; при аварийном обрыве процесса `--rm` выполняет отложенную очистку после срока жизни, если Docker доступен.

Успешное итоговое сообщение модели само по себе ничего не доказывает. Доказательство образуют изменения каркаса, тесты, `patch.txt`, местный `fix.patch`, траектория и повторная оценка в новом контейнере.

## 2. Кто что делает

### Пользователь

- запускает и проверяет llama.cpp;
- выполняет команды PowerShell;
- выдаёт программирующему ИИ-агенту маленькие поручения;
- просматривает изменения;
- проверяет тесты и артефакты;
- не редактирует исходники вручную.

### Программирующий ИИ-агент

- изучает только относящиеся к поручению файлы;
- до правки объясняет договор поведения и способ проверки;
- меняет только разрешённые исходники;
- не ослабляет тесты;
- после правки объясняет смысл каждой части изменения.

### Создаваемый CodeAgent

- получает постановку задачи;
- предлагает структурированные вызовы `execute`, `invoke_skill` и `send_message`;
- исполняет команды не на Windows, а через `Environment.execute` в контейнере;
- работает в `/testbed`;
- создаёт `patch.txt` внутри контейнера.

## 3. Местная архитектура

```text
problem_statement
       |
       v
Agent.build_prompt
       |
       v
llama.cpp на http://127.0.0.1:8080/v1
       |
       | assistant + tool_calls
       v
общий Agent.run
       |
       v
CodeAgent.execute_tool_calls
       |
       v
Environment.execute
       |
       v
эфемерный Linux-контейнер Docker
       |
       +-- /testbed
       +-- результаты команд
       +-- patch.txt
```

Внешнее поведение задания сохраняется:

- каталог задачи — `/testbed`;
- команды внутри него — Linux-команды;
- `Environment.execute` возвращает структурированный результат;
- `patch.txt` создаётся в среде агента;
- `fix.patch` записывается на Windows после выхода агента;
- оценка применяет патч к чистой копии.

Изменился только поставщик изоляции: вместо внешней среды используется местный Docker.

## 5. Договор сообщений

### `system`

Первое сообщение содержит постоянные правила, роль агента, сведения о среде и краткий каталог навыков, если навыки загружены.

Сведения о системе относятся к Linux-контейнеру, а не к Windows. Значения берутся из:

- `environment.machine`;
- `environment.release`;
- `environment.system`;
- `environment.version`.

Официальное условие требует блок следующей структуры:

```text
<system_information>
{
  "machine": <machine>,
  "release": <release>,
  "system": <system>,
  "version": <version>
}
</system_information>
```

Поручите агенту безопасно сформировать этот блок, но не диктуйте готовое тело метода.

### `user`

Вторым сообщением идёт исходная постановка задачи. Она не должна растворяться в системных указаниях или заменяться кратким пересказом.

### `assistant`

Сохраняется нормализованный ответ модели целиком. Он может включать:

- текст;
- сведения о рассуждении;
- один вызов инструмента;
- несколько вызовов.

Нельзя оставить только `content`: тогда будут потеряны `tool_calls`.

### `tool`

Каждый вызов получает отдельное сообщение:

```json
{
  "role": "tool",
  "tool_call_id": "call_x",
  "content": "<строковое наблюдение>"
}
```

`tool_call_id` связывает наблюдение с вызовом в пределах одного ответа `assistant`. Поставщик вправе повторить такой же ID на другом шаге, поэтому глобальный словарь по ID ненадёжен.

Если один ответ содержит два вызова, следующий запрос должен содержать:

```text
assistant(tool_calls=[A, B])
tool(tool_call_id=A)
tool(tool_call_id=B)
```

Qwen в проверенном профиле умеет вернуть два вызова в одном ответе. Каркас всё равно обязан корректно обрабатывать список любой допустимой длины.

## 6. Рабочая история и журналы

В заготовке уже есть:

- `api_prompts` — снимки фактически отправленных запросов;
- `api_responses` — нормализованные ответы API;
- `compaction_events` — события будущего сжатия;
- `steps_taken` — число успешных запросов действия;
- `finished` — состояние завершения.

Для ReAct нужна отдельная активная история.

```text
неизменяемые якоря:
  system
  task

активная история:
  assistant_1
  tool_1
  assistant_2
  tool_2a
  tool_2b

журнал:
  снимок запроса 1
  ответ 1
  снимок запроса 2
  ответ 2
```

`api_prompts` нельзя использовать как текущую историю: каждый снимок уже содержит предыдущее, и при объединении сообщения многократно продублируются.

Инварианты:

1. Каждое рабочее сообщение добавляется один раз.
2. `build_prompt()` не меняет состояние.
3. Два последовательных вызова `build_prompt()` дают одинаковый результат.
4. Новый ответ добавляется после запроса.
5. Наблюдения добавляются после исполнения всех вызовов ответа.
6. Общий класс не знает имён предметных инструментов.

## 9. TODO 1.2 — общий цикл ReAct

Один шаг — один успешный запрос следующего действия через `query_language_model()`. Внутренние повторы клиента не считаются новыми шагами каркаса.

Порядок:

```text
проверить остаток шагов
при необходимости сжать контекст
запросить следующее действие
сохранить полный assistant
исполнить все tool_calls
сохранить все tool-наблюдения
проверить finished
```

### Текст без вызова

Обычный текст модели не завершает CodeAgent. Завершение связано с успешным `send_message`.

Если незавершённый ответ не содержит `tool_calls`, каркас:

- сохраняет `assistant`;
- добавляет короткую предметно-независимую реплику `user`, предлагающую продолжить допустимым действием;
- не выдумывает за модель команду;
- не увеличивает счётчик из-за этой реплики.

### Предел шагов

При `step_limit=N` допустимо ровно N запросов действия.

- `step_limit=0` — запросов нет, сразу `StepLimitError`;
- если N-й ответ завершает задачу, запуск заканчивается нормально;
- если N-й ответ не завершает задачу, его вызовы и наблюдения обрабатываются, затем попытка N+1 отклоняется до обращения к модели.

`steps_taken` уже увеличивается внутри `query_language_model()`. Второе увеличение в `run()` даст неверный предел.

### `finished`

Общий цикл только читает общий флаг. Предметный слой устанавливает его по своему договору. В CodeAgent это успешный `send_message`.

### `finally`

Предоставленный блок обязан сработать при:

- нормальном завершении;
- `StepLimitError`;
- окончательном отказе API;
- сбое предметного исполнителя;
- прерывании другого вида.

В местной версии достигнутый `finally` вызывает `stop()` и немедленно удаляет Docker-контейнер. Не меняйте этот обязательный блок: `--rm` — только дополнительная отложенная страховка при обрыве управляющего процесса, а не замена очистки в коде агента.

### Маленькое поручение

```text
Изучи TODO 1.2, query_language_model, maybe_compact_context и предоставленный
finally. До изменения выпиши точную семантику step_limit для значений 0 и 1,
порядок добавления assistant/tool и поведение текстового ответа без вызова.
Реализуй только общий цикл в Agent.run. Не меняй finally, счётчик внутри
query_language_model, подклассы и TODO сжатия. После правки объясни, почему
N+1-й запрос невозможен и почему все вызовы одного ответа закрываются
наблюдениями до следующего запроса.
```

## 10. TODO 1.3 — `execute` и `send_message`

### Регистрация

CodeAgent добавляет `EXECUTE_TOOL` и `SEND_MESSAGE_TOOL` к уже существующему списку. Список нельзя заменять: базовый класс мог добавить `INVOKE_SKILL_TOOL`.

Ожидаемые наборы:

```text
без навыков:
  execute
  send_message

с навыками:
  invoke_skill
  execute
  send_message
```

### Обработка вызова

Для каждого элемента отдельно нужно:

1. сохранить исходный ID;
2. прочитать имя функции;
3. разобрать `arguments` как JSON;
4. проверить объект и аргументы;
5. исполнить только известную функцию;
6. получить строковое наблюдение;
7. вернуть отдельное сообщение `tool`.

Один общий `try` вокруг всего списка опасен: ошибка первого элемента лишит остальные ответов.

### `execute`

Поддерживаемые аргументы определены схемой:

- обязательный `command`;
- необязательные `shell`, `cwd`, `timeout`, `env`.

Они передаются в `Environment.execute`. Значение `cwd` по умолчанию — `/testbed`.

Одна команда выполняется в новой подоболочке Linux. Обычный `cd` или `export` не переносится в следующий вызов; для устойчивого состояния предназначены `cwd` и `env`. Изменённые файлы сохраняются до удаления контейнера.

Ненулевой `returncode` — наблюдение, а не обязательное исключение. Красный тест нужен модели для следующего решения. Длинный вывод форматируется предоставленным `format_tool_output`: сохраняются начало и конец, середина ограничивается.

### `send_message`

Успешный вызов:

- принимает строковый `summary`;
- устанавливает `finished=True`;
- возвращает связанное наблюдение.

Он не создаёт патч. До завершения навык должен привести агента к непустому `patch.txt` внутри `/testbed`. После выхода командный интерфейс читает этот файл.

Если в одном ответе после успешного `send_message` стоят дополнительные вызовы, они не должны менять среду. Каждый всё равно получает отдельное наблюдение об отклонении после завершения.

### Исправимые ошибки

В наблюдение превращаются:

- повреждённый JSON;
- JSON другого верхнего типа;
- отсутствующий обязательный аргумент;
- неверный тип;
- неизвестное имя инструмента;
- попытка действия после завершения.

Каркас не должен «исправлять» JSON или угадывать намерение модели.

### Маленькое поручение

```text

проверки диспетчеризации. До правки перечисли ветви одного вызова и объясни,
почему ненулевой код команды не равен отказу каркаса. Реализуй регистрацию и
диспетчер только для TODO 1.3. Для каждого исходного вызова верни ровно одно

неизвестные имена должны быть восстанавливаемыми. Не используй локальный
subprocess и не меняй Docker-инфраструктуру.
```

## 11. TODO 1.4 — навыки и поэтапное раскрытие

`skills_path` указывает на каталог:

```text
tasks/code-skills/
  submit-task/
    SKILL.md
```

Загрузчик рассматривает непосредственные дочерние каталоги. Каждый `SKILL.md` начинается YAML-заголовком между `---` и содержит:

- `name`;
- `description`.

Для каждого навыка нужны два представления:

- `metadata` — только имя и описание для начального каталога;
- `content` — полный исходный `SKILL.md`, возвращаемый после `invoke_skill`.

Нужно отклонять:

- отсутствующий путь;
- путь не к каталогу;
- дочерний каталог без `SKILL.md`;
- отсутствующую или незакрытую границу YAML;
- YAML не в форме объекта;
- отсутствующие, пустые или неверно типизированные поля;
- одинаковые `name` в разных каталогах.

Поэтапное раскрытие:

```text
до invoke_skill:
  model sees name + description

после invoke_skill:
  model receives full SKILL.md as tool observation
```

Если навыков нет, в запросе не должно быть ни `invoke_skill`, ни `patch.txt`, ни инструкции сдачи.

### Маленькое поручение

```text
Изучи TODO 1.4, формат tasks/code-skills/*/SKILL.md и относящиеся проверки.
До изменения опиши границу поиска, правила YAML, обработку дубликатов и
различие metadata/content. Реализуй только загрузку навыков, краткий каталог
и вызов invoke_skill. Полный текст навыка не помещай в system_prompt.
Повреждённый каталог должен давать ясный ValueError, неизвестное имя при
вызове — связанное восстанавливаемое наблюдение.
```

```powershell
uv run pytest
```

TODO частей 2 и 3 могут ещё оставлять ожидаемые падения. Инфраструктурные проверки должны оставаться зелёными:

```powershell
uv run pytest tests/test_infrastructure.py tests/test_smoke.py
uv run pytest local_tests -m local -v
```

Ожидаемые проверенные итоги неизменной инфраструктуры:

```text
3 passed
61 passed
```

Набор из 61 местной проверки также подтверждает, что обычный `exec` передаёт пользовательские `argv` и `env` контейнерному исполнителю JSON-ом через stdin, контейнер запускается с `--init`, а `--rm` удаляет оборванный контейнер после `deployment_timeout` при доступном Docker.

## 13. Путь CodeAgent в `/testbed`

Программная задача сообщает о дефекте шахматной службы. Учебная ценность — в инженерной последовательности, а не в знании конкретной правки.

### Воспроизвести

CodeAgent должен:

- осмотреть `/testbed`;
- найти относящиеся к поведению файлы и проверки;
- выполнить сценарий воспроизведения;
- сохранить фактический код ответа и диагностический вывод;
- отличить подтверждённый факт от гипотезы.

### Исследовать

Агент прослеживает поток данных и сравнивает:

- завершающий допустимый ход;
- обычный незавершающий ход;
- ожидаемое состояние и фактический отказ.

Не сообщайте ему точное условие или строку исправления.

### Исправить узко

Изменение должно:

- исправлять только подтверждённую причину;
- сохранять прежнее поведение обычной партии;
- не маскировать исключение общим перехватом;
- не менять тесты;
- не добавлять временные файлы в патч.

### Проверить

Агент должен получить свидетельства:

- исходный сценарий воспроизводился до правки;
- целевая проверка проходит после правки;
- регрессионные проверки проходят;
- `git diff` содержит только относящееся изменение;
- патч применим от чистой исходной точки.

### Подготовить патч

Подробный порядок находится в навыке и должен быть раскрыт через `invoke_skill`. Руководство не воспроизводит его. Итогом внутри контейнера становится `patch.txt`.

## 15. Настоящий запуск CodeAgent

Команда выполняется из корня `assignment-1`:

```powershell
$codeAgentArgs = @(
  'assignment-code-agent'
  '--model'; 'Qwen3.6-27B-Q6_K'
  '--task'; 'tasks/chess-terminal-move'
  '--step-limit'; '200'
  '--skills-path'; 'tasks/code-skills'
  '--trajectory'; 'artifacts/part1-qwen-run-01-trajectory.json'
  '--patch-output'; 'artifacts/part1-qwen-run-01.patch'
)
uv run @codeAgentArgs
```

Поток:

```text
Task.load
  → проверка закреплённого chess_app
  → сборка или использование чистого местного образа
  → новый контейнер с /testbed
  → CodeAgent.run
  → patch.txt внутри контейнера
  → чтение patch.txt
  → artifacts/part1-qwen-run-01.patch на Windows
  → удаление контейнера
```

Пути содержат номер попытки. Не перезаписывайте предыдущую траекторию новым запуском.

Если агент вызвал `send_message`, но `patch.txt` отсутствует или пуст, командный интерфейс завершится ошибкой. Это правильная защита от ложного успеха.

## 16. Независимая оценка патча

Оценивайте патч именно той же попытки:

```powershell
uv run python scripts/evaluate.py --task tasks/chess-terminal-move --evaluation tasks/chess-terminal-move/public_tests --patch artifacts/part1-qwen-run-01.patch -v
```

Оценка:

1. создаёт свежий стенд из закреплённого исходника;
2. применяет патч кандидата;
3. добавляет открытый проверочный патч;
4. запускает целевой и регрессионный наборы;
5. при штатном выходе немедленно удаляет контейнер; при обрыве процесса отложенное удаление обеспечивает `--rm`, если демон Docker доступен.

Успех требует одновременно:

```text
FAIL_TO_PASS 1/1
PASS_TO_PASS 9/9
RESOLVED: yes
exit code 0
```

Если какая-либо строка отличается, патч ещё не доказан.

После успешной оценки можно скопировать согласованную пару под основные имена:

```powershell
Copy-Item -LiteralPath 'artifacts/part1-qwen-run-01.patch' -Destination 'artifacts/fix.patch'
Copy-Item -LiteralPath 'artifacts/part1-qwen-run-01-trajectory.json' -Destination 'artifacts/part1-trajectory.json'
```

Затем ещё раз проверьте основной путь:

```powershell
uv run python scripts/evaluate.py --task tasks/chess-terminal-move --evaluation tasks/chess-terminal-move/public_tests --patch artifacts/fix.patch -v
```

## 17. Как проверить траекторию

Не ограничивайтесь существованием JSON. Найдите в `part1-trajectory.json` свидетельства:

- первый запрос содержит один `system`, задачу и верные сведения Linux;
- Qwen вызывает только зарегистрированные инструменты;
- каждый `tool_call` имеет связанное наблюдение;
- несколько вызовов одного ответа обработаны полностью, если встречались;
- CodeAgent сначала воспроизводит дефект;
- гипотезы проверяются командами;
- после правки запускаются целевые и регрессионные тесты;
- `invoke_skill` предшествует использованию подробной инструкции;
- агент завершает работу только после подготовки патча;
- журнал не содержит `.env` или значения настоящих секретов.

Траектория должна соответствовать именно тому патчу, который оценён.

## 18. Типичные ошибки

- Активная история строится из `api_prompts` и многократно дублируется.
- `build_prompt()` изменяет состояние.
- Сохраняется только текст `assistant`, а вызовы теряются.
- Два вызова получают одно объединённое наблюдение.
- ID считается глобально уникальным.
- Текст без инструмента преждевременно завершает запуск.
- Лимит разрешает запрос N+1.
- `steps_taken` увеличивается второй раз в `run`.
- `maybe_compact_context()` вызывается после запроса, а не до него.
- Ненулевой код теста превращается в фатальное исключение.
- Повреждённый JSON автоматически исправляется.
- Неизвестное имя исполняется через произвольный `getattr`.
- Новый список инструментов затирает `invoke_skill`.
- Навыки ищутся рекурсивно.
- Дубликат имени навыка молча перезаписывается.
- Полный `SKILL.md` попадает в начальный запрос.
- Без навыков запрос всё равно раскрывает `patch.txt`.
- Сведения системы берутся с Windows.
- CodeAgent запускает местный `subprocess` вместо `Environment.execute`.
- Исправление вносится в местный `chess_app`.
- Успех объявляется по одному тесту в уже загрязнённом каталоге.
- Меняется предоставленный `finally`.

## 19. Критерии готовности

Часть 1 завершена, если:

- общий `build_prompt` чист и предметно-независим;
- активная история отделена от журналов;
- роли и порядок сообщений корректны;
- несколько вызовов получают отдельные наблюдения;
- текстовый ответ не завершает CodeAgent;
- предел шагов точен;
- ошибки действия восстанавливаемы;
- `execute` использует только контейнерный `Environment.execute`;
- сведения системы описывают Linux-контейнер;
- навыки проверяются строго и раскрываются поэтапно;
- `finally` сохранён;
- Qwen создаёт непустой патч и траекторию;
- `fix.patch` даёт `1/1`, `9/9`, `RESOLVED: yes`;
- после запуска нет контейнера;
- `tests/`, `tasks/` и `chess_app/` не изменены;
- в артефактах нет `.env`.
